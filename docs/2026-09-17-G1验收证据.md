## 3. 关键证据

### 3.1 空库时仪表盘显示 0 而不是 1247（计划 G1 验收第 ④ 条）

清空 `complaint` 后请求 `/dashboard/overview`：

```json
metrics = {"total":0,"todayReceived":0,"waterReceived":0,"gasReceived":0,
           "sensitiveTotal":0,"closedInSystem":0,"overtimeActive":null,"closedRate":null}
unavailable = [{"key":"overtimeActive",...G2},{"key":"closedRate",...G5/G6}]
响应体是否含 1247 / 78.5 / 683 / 564 / sensitiveCount:28  ->  False
```

**不可计算的指标返回 null 并列入 unavailable，不是伪造 0；可计算的返回真实 0，不回退常量。**

### 3.2 审计留痕（A9）

```text
action                | result    | app_code | count
INTAKE_CREATE         | success   | gqxq     | 2
INTAKE_DUPLICATE_SAME | duplicate | gqxq     | 2
INTAKE_REDELIVERY     | success   | gqxq     | 2
LOGIN                 | success   | gqxq     | 2
LOGIN_FAILED          | failure   | gqxq     | 2
```

复用既有 `operation_audit_log`，未新建 audit_log 表。

### 3.3 数据库不可达时拒绝启动（A11 之一）

把 `GQXQ_DB_PORT` 指向无人监听的 3307：

```text
exit code = 1
[startup] 数据库不可达，拒绝启动。connect ECONNREFUSED 127.0.0.1:3307
```

### 3.4 运行期数据库故障不回退 Mock（A11 之二，最关键）

服务正常运行中把 `complaint` 表改名制造查询故障，再改回：

| 阶段 | /complaints | /dashboard/overview |
| --- | --- | --- |
| 故障前 | HTTP 200 + 真实数据 | — |
| **故障中** | **HTTP 500 `INTERNAL_ERROR`，body 内无任何诉求数据** | **HTTP 500，无任何指标数据** |
| 恢复后 | HTTP 200 + 真实数据（连接池自动恢复） | — |

故障中的响应体：`{"code":500,"message":"服务端内部错误","data":{"errorCode":"INTERNAL_ERROR","requestId":"..."}}`

**这是禁止 Mock 回退被工程化的判定性证据：数据库坏了就是 500，不存在任何看起来还能用的假数据。**

## 5. 本轮修掉的数据缺陷（M5）

接入真实接口时暴露的三处**数据**不一致（非代码缺陷）：

| 问题 | 处理 | 验证 |
| --- | --- | --- |
| `dict_item.urgency_level.critical` 标签是重大，而 `enums.ts` 是特急 | 以 enums.ts 为标签唯一真源修正 | 字典返回 `critical:特急` |
| `complaint_type` 字典缺 `report`（举报） | 补字典项 | 字典返回 4 项，含 `report:举报` |
| `complaint.district_code` 全为 NULL，区域筛选永远 0 条 | 登记 `district` 字典（GB/T 2260），回填可精确匹配的行并留痕 | `420502`→5 条、`420503`→2 条、未知→0 条 |

「高新区」不是标准行政区划，**保持 NULL 不猜测**；判据已写进迁移日志。
