## 2. 网关拓扑（现状两套，口径不同）

```
【本机开发 · 3100】
  浏览器/脚本 ──> 127.0.0.1:3100  （M1 后默认只绑回环；非回环地址直连 ECONNREFUSED，见 §4-A1）
                 └─ MySQL 127.0.0.1:3306

【云上实例 · 〈东京 VPS〉】
  公网 ──HTTPS──> nginx:443（〈AI 中转主站域〉，与既有站共用一个 server）
                    ├─ location /gqxq/            -> 前端静态产物
                    ├─ location /gqxq/api/        -> proxy_pass http://127.0.0.1:3100/api/   （带 X-Forwarded-For 等）
                    │                              limit_req 10r/s burst=20、limit_req_status 429、client_max_body_size 1m
                    └─ location /gqxq/api/v1/external/ (+3 条 = 精确匹配) -> **return 403**（入站封闭，放开前不得摘）
                 docker bridge: gqxq-net
                    └─ 127.0.0.1:3100 -> 3100 （gqxq-server 容器；gqxq-mysql 不发布任何宿主机端口）
```

要点：**3100 从未直接暴露公网**；公网到 E1 的唯一通路被 nginx 的 403 挡住。
`/gqxq/api/` 那条反代**已经在发 X-Forwarded-For**，所以 §3 的 `GQXQ_TRUST_PROXY` 取值不是纸面约定，
而是"放开入站那天 remote_ip 记的是客户端还是网关"的直接开关。

## 3. 监听与来源 IP 的配置基线（M1 + M3 的仓库侧）

| 环境 | `GQXQ_HOST` | `GQXQ_TRUST_PROXY` | 为什么 |
| --- | --- | --- | --- |
| 本机开发（3100） | 不设 ⇒ 默认 `127.0.0.1` | 不设 ⇒ 默认 `loopback` | 只绑回环；同机直连时 `req.ip` 就是连接对端，XFF 无从伪造 |
| 裸机 + 本机反代 | `127.0.0.1`（默认） | `loopback`（默认） | nginx 与后端同机 ⇒ 回环对端可信，XFF 里的真实来源被采信 |
| **云上容器形态（现行）** | **必须显式 `0.0.0.0`** | **必须 `private`（等价 `uniquelocal`）或直接写 docker 网关 IP** | 容器里绑 `127.0.0.1` 会让宿主的 `127.0.0.1:3100->3100` 发布端口**不通**；nginx 在宿主，经 bridge 网关进来，`loopback` 不认这个对端 ⇒ XFF 被忽略、`remote_ip` 全记成网关 IP |
| 排障 | — | `true`（会启动打警告） | 任意来源可伪造留痕 IP，**禁止**作为白名单判定或追溯依据 |

代码位置：`server/src/config/env.ts`（`host` / `trustProxy`）、`server/src/index.ts`（显式 bind + 非回环警告）、
`server/src/app.ts`（`applyTrustProxy`，非法取值启动即抛）。
新增 env 已登记进 `server/.env.example`（含 `GQXQ_BASELINE_*` 阈值项）。

⚠️ **部署侧待办（本批未做，属后续部署批次）**：`/data/gqxq/.env` 尚未写入
`GQXQ_HOST=0.0.0.0` 与 `GQXQ_TRUST_PROXY=private`。**在含 M1/M3 的构建上云之前必须先补这两行**，
否则容器起得来但发布端口不通（表现是"health 超时"而非报错），放开入站后 `remote_ip` 还会整片变成网关地址。

A6 的读法：合法基线就是"**一个投递方 + 一天内一次性批量导入**"。
今后任何一个日子上出现第二个 `remote_ip`、或日均 `created` 从个位数跳到几百，都属"超出基线"，
这正是要在放开入站前先有告警的原因（M4 的默认阈值即按此定：`created>50 / deliveries>200 / rejected>5 / distinct_ip>3`）。

| JSON body 边界 | 实际来源路径上的 1 MiB JSON 数组加空白可通过解析并到达业务拒收（400，替身记录两次 INSERT）；1 MiB + 1 字节返回 `413/PAYLOAD_TOO_LARGE` 且零 SQL；非法 JSON 返回 `400/VALIDATION_FAILED` 且零 SQL | 未压缩 JSON 的应用解析边界；不代表 nginx body/限流策略，业务校验也不是身份认证 |
| 默认 proxy | 非回环 socket 的伪造 XFF 被忽略；回环 socket 的 XFF 被采信；多跳链停在最近的不可信 hop，不接受攻击者前置值 | Express 对当前信任规则的实际 IP 计算与请求上下文留痕；不是来源 IP 白名单或真实反代链验收 |
| 其他 proxy 配置 | `off` 忽略回环 XFF；明确 CIDR 只信配置段；`private` 正确编译为 `uniquelocal`；非法配置抛错；`true` 警告且接受伪造 XFF | 现有配置分支和失败语义；不能用 `true` 证明来源身份 |
| 已知认证缺口 | 无 Bearer/签名的业务无效报文可到达来源拒收处理器并尝试写拒收日志/审计（内存替身），返回业务 400；普通 `/complaints` 无 Bearer 返回401 | 明确证明来源路由没有用户身份门禁；两次合成 INSERT 不是真实库写入，也不构成来源认证通过证据 |

**对历史 §3 用语的当前补充：**默认 `loopback` 并不意味着“同机直连时 XFF 无从伪造”。
任何能直连回环端口的本机进程都属于可信 socket，可自己设置 XFF；本轮 HTTP 测试确认其值会进入
拒收日志的 `remote_ip`。可信代理应由网络隔离及覆盖/净化转发头的实际网关配置共同保证。
`runAsTrustedSystem` 仅为原有机器入口建立内部授权上下文，不验证来源身份，不补签名或网络边界。

### 10.2 来源身份认证：待协议、待联调

当前 `externalYijiejieban.ts` 仍没有 token、签名、时间窗口、重放或 IP 白名单验证器。
载荷分类/字段校验、业务幂等摘要、代理 IP 留痕和内部 machine context 都不能替代来源身份认证。
public-utility callback 有其独立回调契约，不能移植为宜接就办的来源协议。
历史六段 HMAC 方案仅是建议蓝本，本轮未取得双方同意的协议，因此未新增或激活验证器。

| 验收项 | 当前状态及所需证据 |
| --- | --- |
| 缺凭证/坏签名 | **待协议、待联调**：需双方确认凭证/签名字段、算法及规范化规则、原始字节范围、失败状态与回执。不得将业务400或本地回调验签标为来源认证PASS |
| 过期请求 | **待协议、待联调**：需确认时间字段、时区/单位、允许时间窗口和时钟偏差 |
| 重放 | **待协议、待联调**：需确认唯一重放键、去重保留期、持久化/并发语义与合法重传区别 |
| 密钥轮换 | **待协议、待联调**：需确认 keyId/版本、有效期、旧新密钥重叠及吊销处理 |
| 错误来源 IP | **待来源出口段与网络验收**：应用无 IP 白名单，需明确真实 socket/反代拓扑及来源段，再验收拒绝语义 |
| 伪造代理头 | **本地 Express 信任边界已测；网关处理待实测**：需证明真实 nginx 对 XFF 的覆盖/追加策略与可信 hop 配置，以及直连路径隔离 |

未为不存在的协议编写“坏签名/过期/重放/IP 拒绝”的假通过测试。
这些缺口不阻断后续 B 批本地开发，但本轮不能宣称来源认证联调完成。

### 10.3 网关/公网：本轮未验证

本轮未运行 SSH、`nginx -T`、公网探针、安全组/防火墙查询、容器发布端口核验或真实服务重启。
nginx 403、IP allow/deny、`limit_req`、`client_max_body_size`、直连隔离及转发头策略均需
外部网关验收并登记当前配置/时间/证据路径；历史 §4 与 §5.1 不能替代这些新证据。
也未运行旧 `baseline:intake`、`verify-intake-baseline` 或 `verify:hardening`，未使用真实诉求作验证样本。
