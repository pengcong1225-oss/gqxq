# 诉求系统最小交付补齐说明

日期：2026-10-15。依据为最新《技术方案_彭聪.docx》诉求章节、已确认的外部办理及回访分工。本轮仅完成本地后台改动，未部署、推送或操作生产数据库。全部改动留在当前 worktree，供整批复核。

## 本轮实现

- 挂载 `GET /api/v1/complaints/:idOrNo/source-processes`，使用 `complaint.read` 和当前案件范围校验。详情页接入来源全过程表，保留修订、缺时间和未接入提示。姓名及电话在当前节点和历史版本均受 `source_document.read` 控制。
- 新增签名来源过程推送入口，保存来源规定完成时间和实际完成时间；缺值仍显示来源未提供，不使用交办、接收或本地办结时间替代。每次更新的来源版本、日期、截止时间和内容摘要写入审计。
- 新增 `procurement-source-completed-v2` 采购统计政策：仅宜接就办、现有真实状态映射中的 `completed`、供水或供气，并有来源状态同步和来源录入时间证据。`closed` 只代表来源关闭，不当作办结。按来源录入时间归属期间，缺依据记录排除并返回原因。总账和纠偏后分析库保持独立。
- 新入库统计快照使用版本 2，保存来源身份、状态和同步证据；版本 1 仍可读取。旧快照缺来源证据时，新采购政策明确排除，不使用当前案件状态补写旧事实。历史研判移除“本地办结或来源关闭”的替代条件。
- 满意度使用每诉求当前来源版本中的末次唯一、有来源时间、已接通且有有效评价的回访。缺时间、同时间多记录、末次未接通或无评价均不猜测。全部参与选择的当前记录及绑定证据冻结，包含有效、无效和冲突记录，可复算排除原因；不冻结备注或联系人等无关字段。
- 新增 `procurement-statistics` 固定模板版本 `v1`，包含期间及截止时间、供水供气分项、类型、区域、高频小区编码、企业、比较、趋势、满意度、指标与完整性说明，可导出 DOCX/XLSX。沿用任务、冻结快照、权限、租约和已保存字节下载机制。旧 `statistics-draft` 模板及原渲染版本保留。
- 企业增加大屏开关及显示名；服务网格增加管理人和电话。API、表单、CSV/XLSX模板、字段说明与导入校验保持一致。新企业大屏显示默认关闭；旧模板不包含新增可选列时仍可使用。既有网格管理人变更沿用覆盖版本维护流程，需新的有效日期，不改写旧版本。

## 本方接收契约

配置使用现有 `GQXQ_BUSINESS_SOURCES_JSON`。签名 `sourceId` 必须为 ASCII 标识，业务来源名称通过配置 `sourceSystem` 显式映射；不能将中文业务名称直接放入 HTTP header。

```json
[
  {
    "sourceId": "yjjb",
    "sourceSystem": "宜接就办",
    "keyId": "replace-key-id",
    "secret": "REPLACE_WITH_AT_LEAST_32_RANDOM_CHARACTERS",
    "maxSkewSeconds": 300,
    "complaintTargets": [
      {"sourceSystem": "宜接就办", "enterpriseCodes": ["REPLACE_WITH_REAL_ENTERPRISE_CODE"]}
    ]
  }
]
```

示例中的来源、密钥及企业编码需由实施人员配置，不代表已存在真实连接。回访来源可以是其他外部业务系统；为它单独配置 ASCII `sourceId`、密钥及目标来源/企业范围即可。只有明确配置 `allEnterprises: true` 才授予该目标来源全企业范围；未配置目标范围默认不授予回访写入权。

`POST /api/v1/external/business-source/processes` 使用现有四个 header：`x-source-id`、`x-key-id`、`x-source-timestamp`、`x-source-signature`。时间为带时区 ISO 8601，签名为 `HMAC-SHA256(secret, timestamp + "\n" + 原始正文)` 的十六进制值。

```json
{
  "sourceSystem": "宜接就办",
  "sourceId": "SOURCE_CASE_ID",
  "sourceVersion": 1,
  "complete": true,
  "cutoffAt": "2026-10-15T09:00:00+08:00",
  "deadlineAt": "2026-10-14T18:00:00+08:00",
  "completedAt": "2026-10-14T17:00:00+08:00",
  "nodes": [
    {
      "sourceSystem": "宜接就办", "sourceId": "SOURCE_CASE_ID", "nodeId": "NODE_ID",
      "sourceSequence": 1, "sourceVersion": "1", "occurredAt": "2026-10-14T17:00:00+08:00",
      "stage": "办结", "department": null, "contactName": null, "contactPhone": null, "opinion": null
    }
  ]
}
```

案件必须先已接收，身份须与配置映射和案件匹配。来源快照版本为递增整数；同版同内容幂等、同版异内容冲突、旧版本不覆盖。完整批次必须有截止时间。节点按稳定编号保存观察和修订；不因批次未列出某个节点而删除历史节点，撤回需来源提供明确的新版本事实。过程推送不将案件状态自动改为来源已办结；来源状态继续使用现有受控状态同步路径。

外部回访仍通过 `POST /api/v1/external/business-source/events`。接收端按配置的目标来源/企业范围校验数据库中的真实案件，不能依赖正文自报企业授权。新版本的当前头和历史修订均保存 `followup_binding`。既有无绑定记录继续作为来源历史可查，但不计入新采购满意度；须提供经授权的新来源版本，不自动追认旧数据。

## 未验收与剩余边界

- **真实来源联调**：宜接就办过程、期限、完成时间、录入时间、来源办结状态码/撤销更正契约、历史覆盖及接入身份；外部回访系统的密钥、案件绑定、字段映射及真实回执。本方契约可用于联调，不代表已经接通生产来源。
- **业务确认**：日历比较/闰日截短规则、末次回访与多来源优先规则、人口指标及有效历史户数范围。现有实现和排除说明均版本化保留，不宣称业务批准。
- **MySQL验证**：新迁移、实际SQL幂等/并发/回滚、来源版本冲突、报告任务及权限在真实独立 `_test` 库验证尚未执行；现有纯规则和HTTP替身测试不能替代。
- **CIM最后独立处理**：供水/供气/诉求动态三板块；真实地图底图和坐标系；小区、四类停供及施工管线/影响范围图层；多网格联动高亮、项目选择及授权下钻；统计/满意度/研判与同一批次数据对齐。企业大屏开关与显示名仅为后台字段，不能算CIM页面已完成。缺真实几何仍显示资料缺项，不生成虚构坐标或示意实测管线。
- **统一底座/IRS及事件反馈**：身份与组织关联、可信接口契约、真实反馈回执/查询与对账均需联调。既有停供施工只读、实际复供后24小时联动、研判与预警保留，本轮没有重建本地办理、审批或回访流程。

## 2026-10-17 菜单复核及整体纠偏入口恢复

本节依据原始采购文件《[420501202601000760-01F]宜昌市住房和城市更新局城镇供水、燃气用户端管理系统（一期）采购项目（包1）》诉求子系统条款、最新技术方案及知识库 `02-业务规则与主流程.md`。原始采购文件后台1.4、1.6、1.7、1.14分别要求完善地址、敏感交办、精准分类、统计及固定报告；大屏2.8—2.11分别要求网格对比、历史同期诉求研判、预警及保障季数据研判。采购功能不要求每项必须成为独立菜单，已确认业务规则也不能因菜单精简而删除。

### 纠正本次入口调整的范围

此前移除“诉求核验”独立菜单时，只接回地址和分类快捷入口，错误地隐藏了整体纠偏能力。本次恢复原 `AddressCorrection` 工作台至 `/complaints/corrections`，从诉求列表工具栏、行操作及详情进入，导航始终归属“诉求管理”。原 `/address-correction` 链接保留兼容跳转及诉求编号，不再强制变成只改地址。

原工作台继续保留企业名称/归属、地址/位置、诉求性质/正式分类、摘要和企业处置结果的逐项修改、核验无误、依据、版本冲突、历史处理及分析入库结果。纠偏覆盖全部诉求，与交办并行。来源事实、外部填报审批结果、用于本地分析的数据确认分别留存；审批通过不能替代整体纠偏，纠偏也不能代替企业审批。没有新增审批引擎，没有修改来源回传、纠偏服务、分析准入、统计政策、存量快照或历史数据。

详情页补接已有 `POST /complaints/:id/close` 的人工办结接口：具备 `complaint.close` 权限、最终审批通过、无未处理纠偏项、填写依据后才可显式提交；服务端在事务中再次检查原有条件，保存确认人、时间及依据。该动作不修改来源状态，也不代替交办归档。它是既有业务流程的页面入口补齐，不是新建核查流程。

## 2026-10-18 已确认业务流程完整复验

范围：整体纠偏、敏感交办及最终回传、人工办结、分析入库与交办归档。沿用既有业务确认规则，不增加菜单、审批层级、人工回访或重新导入历史数据。纠偏与交办并行；内部分析准入仍为全部纠偏处理完成、最新交办的已应用最终审批证据及对应结果核验；人工办结是独立显式动作，不新增“必须先人工办结才能入分析库”的门槛。

### 实际发现并修复

1. 人工办结原先仅检查诉求汇总 `reporting_status=approved`，新交办尚未完成时可能沿用旧轮审批。现在在同一诉求锁内核对最新交办的最终审批事件及对应结果核验，复用分析准入的证据读取；并发点击仍只有一次办结留痕。
2. 位置组保存或其他字段修正后，已完成的位置项会误报版本冲突并要求再次核对。已处理位置项不再要求重复确认；未完成草稿的真实版本冲突、切换账号/诉求和迟到响应保护保留。
3. `complaint` 中旧的纠偏/分析汇总标志未随所有路径更新，详情可能在实际入库后仍显示“待纠偏、未入库”。列表、详情与纠偏筛选改为按现存纠偏和分析记录读取，不批量改写历史诉求或重开流程。
4. 新旧表的交办快照键排序规则不同，实际签名回传出现 MySQL 1267。新增 `20261018090000__dispatch_snapshot_key_collation.js`，只将快照关联键对齐交办表，保留字段长度、空值约束和签名报文原始字节；重复执行安全。已应用于本地验收库和专用浏览器测试库，未应用生产库。
5. 已完成交办不属于“进行中交办”，详情原提示“尚无交办记录”容易诱导重复交办，改成“当前无进行中的交办，历史结果见填报事项结果”。事项列表展示实际交办进展，避免旧 `external_status` 默认值与已回传审批进展矛盾。
