## 3. 五处模型与现实的缺口（本次核对的主要产出）

### 3.1 `source_id` 不能假定唯一

466 行只有 464 个不同的「案件公文号」：`DH202604060770` **出现 3 次**，录入时间完全相同、内容几乎相同（其中一条多了「1、」前缀）。
这是**源头重复记录**，不是三条不同诉求。我们的 `uk_source(source_system, source_id)` 会正确地把它收敛为一条——本次导入正好可以实测去重与留痕。

### 3.2 `complaint_type` 枚举装不下真实分类（10 条无法映射）

| 来源值 | 条数 | 我们的枚举 |
| --- | --- | --- |
| 求助类 | 4 | 无 |
| 其他类 | 4 | 无 |
| 表扬类 | 2 | 无 |

**其中「表扬类」根本不是诉求**（内容是表扬工作人员尽职责），让它走督办/交办流程没有业务意义。
选项：扩展枚举（新增 help/other/praise）／映射到最接近值并保留原值／跳过这 10 条。

### 3.3 责任企业名称对不上（G2 匹配会大面积失败）

导出里没有独立的「责任企业」列，企业混在 `部门名称` 与 `二级单位` 里：
出现的是 **中燃宜昌公司、夷陵中燃公司、浦华三峡水务、宜昌城发集团** 等；
而我们 `enterprise` 表登记的是 **宜昌中燃城市燃气有限公司、宜昌市供水总公司、点军区供水有限公司、宜昌蓝天气体有限公司**。

**两边名称与编码体系不一致**（「中燃宜昌公司」≠「宜昌中燃城市燃气有限公司」；「浦华三峡水务」我们表里没有）。
结论：真实对接前必须先统一企业主数据编码，否则自动匹配与交办推送都会指向不同主体。

### 3.4 导出里没有任何坐标

26 列中含「经/纬/坐标/lng/lat」的列：**0 个**。`定位情况` 只是标志位（已定位 198 / 无需定位 226 / 未定位 42）。
因此 GIS、热力图、`location_lng/lat` **无法用这批数据验证**。

### 3.5 `source_event_status` 有真值，但值域比我们宽

我们有 `unknown/accepted/processing/completed/closed`；导出有 `正常在办/正常结案/超期结案`。
**「超期结案」没有对应值**（2 条）。它可以映射为 `completed` + 一个「来源侧超期」标记，或扩展枚举。
但也要看清：这证明**来源状态是拿得到的**——之前 UI 一直显示「未接入」是因为适配器按 G6 设计关闭，不是因为来源没有状态。

## 4. 导入方案

**推荐：走真实入站接口 `POST /external/yijiejieban/appeal`（而不是直接写库）**，一条一条灌。
理由：这样能同时验证校验、幂等去重、`complaint_source_log` 留痕、规则引擎判定、编号发号器与三轴初始化——
直接 INSERT 只能验证存储，验不到链路。

已知约束：入站 schema 是 `z.object({...})`，**默认剥掉未知键**，只把未知字段名记进日志。
因此来源的原始分类值（如「表扬类」「超期结案」）若要结构化保留，需要给入站 schema 增加一个 `metadata` 字段
（与 public-utility 契约的 `metadata` 语义一致：「仅作展示和追溯，不参与执行」）。这是 2 行的契约补充。
