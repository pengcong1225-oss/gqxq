## 6. 共用实施和验收规则

每个任务依次完成：指定失败用例 → 在隔离环境确认失败原因 → 最小实现 → 针对性回归及类型检查 → 前端真实操作、落库及重启核对 → 留证与独立提交。只读规则任务按其性质选择验证，不机械要求业务写入。
新增 API 遵循当前 `/api/v1`、业务键、`code + name`、UTC ISO 输出和 Asia/Shanghai 业务日约定。
公共 DTO 以 `server/src/types/api.ts` 为真源，同步 `packages/web-admin/src/types/api.ts`；复杂模块可增加独立 DTO 文件并从真源导出。

本地执行采用逐任务固定 schema 的隔离 runner，测试自身再次核验库名、loopback 与 database()，外发使用假传输。原拟议的统一 verify-abcd.mjs 尚未整合；当前证据是逐项原始运行记录，不表示已有可移植的一键全量验收。不能直接把默认连接真实服务的旧 acceptance 脚本全部串起来。
现有 `npm run verify`、RBAC、hardening、地址测试按影响范围纳入；记录确切命令和输出，不把旧 PASS 当当前结果。

每批证据记录：
- 条款/SQ 编号、实现 commit、迁移及规则版本。
- 虚构输入、预期、实际结果与时间；PASS/FAIL/SKIP/MANUAL/NOT RUN。
- 页面、API、数据直查证据；有持久行为时补重启核对。
- 负向场景、缺陷复测、未决依赖与负责角色。
- 本批操作说明；整体部署恢复、集中培训和最终验收属于后续 F，不提前展开。
