## 0. 结论先行

1. **推荐组合 = A（网络隔离）+ B（网关 IP 白名单与限流）+ E（留痕基线告警）作为上线前必须；C2（HMAC 复用回调验签设施）作为建议档，趁"当前还没有真实调用方"把契约定下来。**
2. 上线前**零外部依赖**就能做、且收益最大的一件事：把服务监听地址从"全接口"收敛为可配置（默认回环），由本机反代转发。
   现在 `server/src/index.ts:15` 是 `app.listen(env.port, cb)`，未指定 host，即 `0.0.0.0/::`，
   且 `env.ts` 里根本没有 `HOST`/`BIND` 这一项 —— 也就是说"只在内网"目前**只是文档里的一句承诺，代码与配置都不保证**。
3. 现有兜底（幂等 `uk_source`、字段白名单、受保护列、校验 400）能挡住"人工结论被外部改写"和"脏数据落错列"，
   **挡不住**"垃圾灌入"和"伪造重传覆盖 19 个来源快照列"。前者是容量问题，后者是**业务口径被伪造**的问题。
4. 有一个隐藏前置改造点：**仓库内没有任何 `trust proxy` 设置**（全库 grep `trust proxy|x-forwarded-for` 无命中）。
   一旦按 B/A 套上网关，`req.ip` 与 `complaint_source_log.remote_ip` 会全部变成网关 IP —— IP 白名单与事后追溯**同时失效**。
5. D（mTLS）在本仓库当前形态下成本最高、可行性最低（服务端完全没有 TLS 终止设施），不建议作为前置手段。

## 1. 现状：代码事实（逐条可核）

### 1.1 挂载顺序 —— 该端点确实在鉴权之前

```
server/src/routes/index.ts:22   // 认证口径：/health、/auth/login、/external/* 不要求 Bearer，其余一律要求。
server/src/routes/index.ts:26   root.use(healthRouter);                       // GET /health —— 无鉴权，内部还打一次 DB
server/src/routes/index.ts:27   root.use(authRouter);                         // POST /auth/login 公开；/auth/user-info 在 router 内部单独挂 requireAuth
server/src/routes/index.ts:28   root.use('/external', externalRouter);        // ← 宜接就办入站：无任何鉴权中间件
server/src/routes/index.ts:30   root.use('/external/public-utility', publicUtilityCallbackRouter);  // ← 回调：靠签名鉴权
server/src/routes/index.ts:32   root.use(requireAuth);                        // ← 之后才要求 Bearer
```

- `server/src/routes/externalYijiejieban.ts:3` 明确写着本路由"不要求 Bearer（由 routes/index.ts 保证）"，
  `:80-82` 注册处理器时唯一的中间件是 `asyncHandler`（只负责把 async rejection 转交 errorHandler），
  `:83-87` 整个处理函数只读三样东西：`req.body`、`req.remoteIp`、`req.requestId` —— **没有任何一处读 Authorization / API key / IP 白名单**。
- `requireAuth`（`server/src/middleware/requireAuth.ts:17-45`）只做 JWT 校验，与入站端点无关。
- 精确面：`/external/*` 整段都在鉴权之前，但当前 `/external` 下只有两个真实处理器
  （`yijiejieban/appeal` 与 `public-utility/callback`）。未知的 `/external/xxx` 会继续下落到 `requireAuth` 而得到 401，不构成额外入口。

一次**合法**投递的实际代价（可作为容量评估基线）：
`select … for update` → 2 次发号（`number_sequence` upsert）→ `insert complaint` → `insert complaint_source_log`
→ 1 次敏感词表查询 → `insert operation_audit_log` → 条件性 `insert sensitive_hit`，约 **7–9 条 SQL + 1 个事务**
（`intakeService.ts:245-249`、`:251-255`、`:317-355`、`:517-561`）。
一次**非法**投递的代价也不为零：`logRejectedIntake` 在事务外用连接池写 **2 行**（`intakeService.ts:215-241`）。

### 1.3 已有的验签设施（回调端点）—— 选项 C 的复用依据

`POST /api/v1/external/public-utility/callback` 与入站端点同样挂在 `requireAuth` 之前，但它**靠签名鉴权**：

| 环节 | 实现 | 位置 |
| --- | --- | --- |
| 原始字节缓存 | `express.json({ verify })` 把**未解析的请求字节**挂到 `req.rawBody`（增强声明在 `node:http` 上，因此所有路由都可用） | `app.ts:18-25`、`types/express.d.ts:21-25` |
| 缺原始字节 → 503 | 无法验签属于我方装配缺失，返回 503 而不是 401（401 会让对方永久丢弃事件） | `routes/publicUtilityCallback.ts:30-36` |
| 算法 | `canonical = epochSeconds + "\n" + lowercaseHex(sha256(rawBody))`，`signature = lowercaseHex(HMAC-SHA256(secret, canonical))` | `clients/callbackSignature.ts:30-49` |
| 比较 | 先正则约束 64 位 hex，再 `timingSafeEqual`（常量时间） | `clients/callbackSignature.ts:58-76` |
| 请求头 | `x-public-utility-{key-id,key-version,timestamp,event-id,signature}`，缺任一 → 401 + 审计 | `routes/publicUtilityCallback.ts:38-46`、`services/callbackService.ts:473-494` |
| 顺序纪律 | **先验签、后 `JSON.parse`**，未验签的字节一律不采信 | `callbackService.ts:515-555` |
| 时间窗 | ±300 s；"签名正确但过旧"返回 **503 + Retry-After**（可重试），不是 401 | `callbackSignature.ts:28`、`callbackService.ts:639-662` |
| 防重放 | 靠 `eventId` 幂等（首投与重投返回同一结论），**没有 nonce** | `callbackService.ts:580-637` |
| 密钥缺失 | 未配置密钥 → 503 + 审计，绝不静默放行 | `callbackService.ts:455-471` |

**复用前必须知道的三个短板**（否则会一起复制过来）：

1. `keyId` / `keyVersion` 只被"要求存在"并写进审计，**不参与选密钥**：验签永远用 `env.callback.secret` 这一把
   （`callbackService.ts:515-516`）。照搬到入站就等于**没有密钥轮换能力**。
2. 回调算法的 canonical **不含 method/path/nonce**（`callbackSignature.ts:3-6` 有醒目警告），
   窗口内对同一 body 的**跨端点重放**在算法层面是中性的 —— 对回调无害是因为有 `eventId` 幂等，
   入站侧对应的幂等键是 `(source_system, source_id)` + `payload_hash`（`intakeService.ts:598-610`），语义并不等价。
3. 我方另有一套**更强的 6 段签名**（含 path 与 nonce，且是对方已实现并交叉验证过的算法）：
   `clients/publicUtilityClient.ts:51-64`（`v1 \n METHOD \n path \n timestamp \n nonce \n bodySha256`）。
   入站若要走 HMAC，**建议以这一套为蓝本**（对端可参照 public-utility 的 `HmacRequestAuthenticator` 实现），
   而不是回调那套两段式。

### 2.2 已有兜底能挡住什么、挡不住什么

| 兜底 | 位置 | **挡得住** | **挡不住** |
| --- | --- | --- | --- |
| 幂等 `uk_source` + `payload_hash` | `intakeService.ts:598-610`、`repositories/canonicalJson.ts:20-34` | 同一 `(宜接就办, sourceId)` 被重复建多行；发送方重排 key / 改空白导致的"看起来变了"（canonical 排序后哈希）；完全同包重投只留 1 行日志、不动任何业务列 | **它是去重机制，不是授权机制**：不校验"投递者是否有权写这条 sourceId"。换 `sourceId` 即新建；同 `sourceId` 换内容即覆盖白名单列 |
| 字段白名单（UPDATE 只含 19 列） | `complaintMapper.ts:91-111` + `intakeService.ts:475-477` | 外部报文改写人工结论（企业匹配、纠偏、督办/填报/关闭状态、分析纳入标记）——这类列**根本不出现在 UPDATE 语句里**，代码写错也覆盖不到 | 19 个来源快照列**全部可被任意来源改写**，包括 `is_sensitive` 与三类分类码位 → 统计与大屏可被伪造（A2/A3） |

| 校验 400 + 拒绝必留痕 | `externalYijiejieban.ts:89-116`、`:125-138`、`:141-178`；`intakeService.ts:215-241` | 脏数据落成结构错误的业务行；title 超列宽被前置拦成 400（而不是 500）；非法码位/非法时间格式/经纬度不成对进不来 | 拒绝路径**本身也写 2 行 DB**；坐标只判越界不判真假；码位合法即照写（合法范围内的假值） |
| 包体 1 MiB | `app.ts:18-25` | 单请求超大 body、`entity.too.large` → 413 | `metadata: z.record(z.unknown())` 不限键数与深度（`externalYijiejieban.ts:48`），整包会**同时**落 `complaint.source_payload` 与 `complaint_source_log.payload`（近 2×）→ 按请求数线性放大的存储增长 |
| 审计 / requestId / remote_ip 留痕 | `complaintSourceLogRepo.ts:32-53`、`auditLogRepo.ts:25-46` | 事后可回答"何时、什么报文、结果如何" | 回答不了"**是谁**"：匿名投递无身份；`remote_ip` 上网关后即退化（§1.4-6）；`x-request-id` 由调用方自定 |
| 无鉴权路由的边界 | `routes/index.ts:28-32` | 其它业务接口一律要 Bearer；`source_system` 由代码写死为"宜接就办"（`intakeService.ts:27`），调用方**无法指定**别的来源系统去踩别人的行 | 全部 464 条真实诉求的 `source_system` 恰就是"宜接就办"，即**真实数据整体在可写范围内** |

**一句话总结**：现有兜底把"外部投递"约束成了"只能改来源快照、不能改人工结论"，但没有任何机制把"外部投递"约束成"只有宜接就办能投"。

## 3. 选项对比

评分口径：防护强度 = 对"未授权者能写入真实业务数据"这件事的阻断能力（与可用性/运维成本无关）。

| 选项 | 防护强度 | 本端改造成本 | 对端改造成本 | 对"来源无法配合改代码"的可行性 | 主要失效模式 |
| --- | --- | --- | --- | --- | --- |
| **A 网络层隔离**（防火墙/安全组/内网只放行来源 IP；叠加"服务只绑回环"） | **中-高**：对远程攻击者是硬阻断；对同网段主机为 0 | **最低**：运维配置；本端仅建议加一个可配置 bind host（`index.ts:15`） | **0** | **完全可行**（对端零要求） | ①对方出口 IP 变化/NAT/前置机共享出口；②同网段横向（内网任意主机=合法身份）；③**没有逻辑身份**，换 IP 即换来源；④一次误开放即彻底裸奔（现状正是"无人配置"）；⑤IPv6/回环漏配 |
| **B 网关层**（nginx/APISIX：IP 白名单 + 限流 + 可选静态 header 口令 + 只允许网关连源站） | **中-高**：叠加限流后可同时压制 A5 类灌入 | **低-中**：新增反代配置；**必须同时**设 `trust proxy`（如 `loopback/private`）否则一切按网关 IP 判定 | **0** | **完全可行** | ①**绕过网关直连 3100**（当前全接口监听 + 应用层零校验 → 必须与 A 同用）；②`trust proxy` 误设为 `true` 使 XFF 可伪造，白名单形同虚设；③NAT 后按 IP 限流失准（把合法来源整体限死或放行一整片）；④对方出口被 CDN/代理池化时白名单不可维护 |
| **C1 应用层共享 token**（固定 header，如 `x-intake-token`，等值比较） | **中**：把"任何能连通的人"降为"持 token 的人"；不防篡改、不防泄露后滥用 | **低**：一个中间件（约 30–60 行）+ 一个必填 env（沿用 `config/env.ts` 的"缺失即拒绝启动"纪律，并像回调那样把"未配置"回 503 而非放行） | **极低**：加一个 HTTP 头，**不改报文体** | **多数情况可行**：现实里"不能改报文"通常指"不能改 body 结构"，加 header 往往可谈；若对方只肯改传输层配置（如前置机加头）也适用 | token 长期有效、泄露即永久（现有设施**没有轮换/失效机制**）；无 body 完整性 → 持 token 者可伪造任意 sourceId 与内容（A2/A6 照旧）；抓包即取（必须配 TLS） |
| **C2 应用层 HMAC 签名**（复用回调验签设施，建议采用 6 段 canonical） | **高**：不可伪造、防篡改、时间窗 + nonce 防重放；密钥可轮换（若同时补 keyId→secret 映射） | **中**（估 2–4 人日含联调与验收脚本）：新增验签模块 + 入站中间件；`rawBody` 已全局可用（`app.ts:18-25`），`sha256Hex/timingSafeEqual` 已存在（`clients/callbackSignature.ts:30-76`） | **高**：对方须实现 canonical + HMAC-SHA256 并处理密钥下发 | **取决于对方能否改代码**；若不能，可让**双方任一前置机/网关代签**（成本降到 B 级）；**注意当前无真实调用方（§1.4-2），现在把它写进接口约定最便宜** | 时钟偏移 > 窗口 → 全量 401（需明确返回码语义：入站侧若也回 503 会被误认为"我方故障"）；密钥轮换（照搬回调会缺，见 §1.3-1）；跨端点重放（若沿用两段式，见 §1.3-2）；对方实现偏差导致长期 401（需像 G4 那样做"互为独立实现"的交叉验收） |
| **D mTLS**（双向证书，DN/CA 白名单） | **高**：身份绑到证书而非 IP，抗 NAT/出口漂移 | **高**：服务端**当前没有任何 TLS 终止**（`index.ts:15` 是 `app.listen`，纯 HTTP）；需自建 TLS 或让反代做 mTLS 再把 DN 透传成 header（又回到 `trust proxy` 问题） | **高**：对方要申请/装载/续期客户端证书、改信任库 | **低**：政务环境证书流程通常要走正式申请；若对方形态是"导出文件 + 人工投递"（现状）则完全不可能 | 证书过期/吊销即全量失败且失败面是"整条业务线"；私有 CA 运维负担；仍要防"绕过反代直连"；DN 白名单硬编码在配置里易腐化 |
| **E 保持现状 + 监控告警** | **低**：不阻止任何一次写入，只缩短"发现"距离 | **最低**：告警数据源现成（`complaint_source_log` / `operation_audit_log` / morgan combined 日志），无需改代码 | **0** | 完全可行 | **数据已污染才发现**：大屏/总账/分析报告可能已对外发布；需要合法基线（来源 IP 段、日均量、码位分布）才谈得上异常；攻击者可用海量 `updated/duplicate_same` 淹没信号（A5）；A6 抢号类几乎不可观察 |

补充：**每个选项都不能替代"来源系统身份"这一层**。A/B 认证的是"哪台机器"，C/D 认证的是"持有什么凭证/证书"，
而 `uk_source` 只认"哪个 `sourceId`"。当前缺口是三者中最关键的一环 —— 没有任何机制把"宜接就办"绑定到一个不可伪造的投递主体。

## 4. 推荐组合与落地步骤

推荐组合：**A + B + E 打底（上线前必须），C2 为目标形态（建议档，趁调用方还不存在时把契约谈定），C1 作为 C2 谈不下来时的过渡，D 列作远期可选。**

### 4.1 【上线前必须】不依赖任何外部答复即可闭环

| # | 动作 | 本端改动 | 验收判据 |
| --- | --- | --- | --- |
| M1 | **服务只绑可配置地址，默认 `127.0.0.1`**（新增 `HOST`/`BIND` 一类 env；生产由本机反代转发） | `server/src/index.ts:15` + `config/env.ts`；1 处配置 | 从同网段另一台机器直连端口失败；`/health` 经反代仍 200 |
| M2 | **网络隔离**：安全组/防火墙只放行宜接就办出口 IP（或"只放行网关"），并书面登记该 IP 段 | 无（运维 + 业务方提供 IP 段，见 §5-Q2） | 白名单外来源探测端口不可达；变更单留痕 |
| M3 | **网关 IP 白名单 + 限流**（对 `/api/v1/external/yijiejieban/**` 单独一条 location：allow/deny + `limit_req`，按来源 IP 计数），并**同时**在服务端设 `trust proxy` 为 `loopback`/`private`（否则白名单与留痕一律按网关 IP，见 §1.4-4） | 反代配置 + 1 行 app 设置 | 超阈值返回 429；`complaint_source_log.remote_ip` 记到真实来源而非网关 |
| M4 | **留痕基线 + 告警（E 的最低实现）**：以 `complaint_source_log` 为准，按日统计 `created/updated/duplicate_same/rejected` 四类与不同 `source_id` 数；morgan combined 日志按状态码聚合。基线参考值：**464 条 ≈ 6 个月历史**，即日均新增应为**个位数到几十**，远高于此即异常 | 无（SQL + 日志采集配置） | 告警能触发一次真实演练（测试库用 `GQXQ_TEST_DB_NAME`，禁碰真库） |
| M5 | **把"匿名可写"这一事实从隐性变显性**：路由注释已声明不鉴权（`routes/externalYijiejieban.ts:3`），需补一份**部署文档**记录暴露面、网关拓扑、来源 IP 段与责任人；G1 §11-6 与 R5 的欠账在本文下正式改登记为"由 M3 承接，C2 收尾" | 无代码（文档/登记） | 部署文档存在且写明"公网映射禁止"的可核证据（安全组截图或配置） |
| M6 | **明确"我方配置错误 ≠ 调用方错误"的返回码纪律**（照抄回调的做法：密钥/网关未配置回 503 而非 401/放行，`callbackService.ts:455-471`、`routes/publicUtilityCallback.ts:30-36`）。避免防护上线当天把合法来源永久拒掉 | 若采纳 C1/C2 则随之引入 | 配置缺失演练：接口返回 503 且有审计记录，绝无"静默放行" |

### 4.2 【建议】来源身份不可伪造（本方案真正想解决的问题）

| # | 动作 | 说明 |
| --- | --- | --- |
| S1 | **现在就发出接口约定**：宜接就办入站自 v2 起要求 HMAC 签名头（`C2`）。理由见 §1.4-2 —— 目前**没有既有调用方**，约定属于"新增要求"而非"改造存量"，谈判成本最低 | 蓝本用 `clients/publicUtilityClient.ts:51-64` 的 6 段 canonical（含 `path` 与 `nonce`），而不是回调的两段式；对端可参照其在 public-utility 侧已验证过的 `HmacRequestAuthenticator` |
| S2 | 验签实现复用既有设施：`rawBody`（`app.ts:18-25`）、`sha256Hex`、`timingSafeEqual`、hex 格式先校验（`clients/callbackSignature.ts:30-76`）、**先验签后 `JSON.parse`** 的顺序（`callbackService.ts:515-555`） | 新增位置建议：`server/src/middleware/requireIntakeAuth.ts`，只挂在 `routes/index.ts:28` 之前注册的那一个路由上，**不要**扩大到整个 `/external` |
| S3 | 补齐回调设施的两个短板再搬：**`keyId → 密钥`映射**（支持轮换与"先双发后停用"）与 **nonce 去重缓存**（单实例内存 + TTL 即可；多实例需共享存储）。当前 `keyId` 只留痕不参与选密钥（`callbackService.ts:515-516`） | 否则一次泄露 = 永久可伪造，且无法轮换 |
| S4 | 时间窗沿用 ±300 s 口径（`clients/callbackSignature.ts:28`），但**超窗返回 401 + 明确 reason**，与回调侧的 503 语义区分开：入站方是"来源业务系统重投"，若回 503 会被运维误判为我方故障；报文本身可换时间戳重签，永久失败是正确的 | 需在接口文档里写死，避免对方按回调语义实现 |
| S5 | **谈不下来时的过渡 = C1（共享 token）**：强度低于 HMAC，但把防护面从"任何能连通者"收敛为"持 token 者"，且对端只是加一个 header。必须配：TLS（否则抓包即失）、token 长度与必填纪律（`config/env.ts:8-15` 的"缺失即退出"）、"未配置 → 503" | C1 落地时保留 S2 的中间件位置，后续换 C2 只替换校验函数 |
| S6 | **对端完全无法配合时的应用层兜底（不依赖对方任何改动）**：把入站改成"两态"—— 投递先只写 `complaint_source_log`（park），落 `complaint` 由一个**受 Bearer 保护**的确认接口或人工批处理触发（apply）；或至少加"新建需二次确认、重传需人工放行"的开关 | 代价：来源投递不再实时生效，需业务方接受延迟；好处：A1/A5 类匿名灌入彻底落不到业务表 |
| S7 | 容量护栏：`complaint_source_log` 归档/保留策略（该表按设计**只增不删**，见 `complaintSourceLogRepo.ts:1`，因此"清理"必须作为**归档 + 业务方决策**提出，不能自行 `delete`）；`metadata` 加键数/深度或大小上限（`externalYijiejieban.ts:48`）；给 `/external` 单独一条更小的 body 上限（现为全局 1 MiB，`app.ts:19-25`；真实单行报文实测 1.8 KB / 最大 5.4 KB，见 `docs/2026-09-18-宜接就办466行真实数据导入验收证据.md` §4） | 上限取值以实测样本为基准，不要沿用"通用 1 MiB" |

### 4.3 【可选】远期或特定形态

- **D mTLS**：仅当对方是可控的政务系统、且我方确定由反代统一做 TLS 终止时考虑；当前服务端无 TLS 设施（`index.ts:15`），性价比最低。
- **网络分区加强**：入站写路径独立端口/独立进程（甚至独立 DB 账号，只授予 `complaint`/`complaint_source_log`/`operation_audit_log` 等必要权限），把"匿名可写"的爆炸半径限制在最小列集合。与 A/B/C 正交，属加固项。
- **签名/白名单的验收脚本化**：照 G4 的做法，让投递桩与验签实现**互相独立**（`clients/callbackSignature.ts:42-44` 明确写了这个理由），避免"同一份实现的错误自我掩盖"。
- **`is_sensitive` 由外部可写这一条单独复审**：它同时在白名单（`complaintMapper.ts:91-111`）里被外部覆盖，又是敏感监控的唯一开关（A3）。把它移入受保护列（或改为"只能置 1、不能置 0"）比加防护更直接，但属于业务口径决策，本文不代作决定。

### 4.4 建议的执行时序（供排期）

1. **本周**：M4 + M5（零代码，先让"裸奔"可观察、可登记）；同时向业务方发 §5 的 4 个问题。
2. **上线前**：M1 + M2 + M3（+ M6 纪律）。这三项合起来才等价于"仅内网、仅来源 IP、不可被打满"。
3. **接口约定冻结前**：S1–S4（C2）。若约定窗口错过、对方开始按现状对接，则退化到 S5（C1）+ S6。
4. **每季度**：轮换演练（依赖 S3 的双密钥映射）+ 告警基线复核（M4 的日均阈值随真实业务量重设）。
