## 0. 结论先行（三句话）

1. **留痕也脱**（唯一需拍板项）：`complaint.source_payload` 与 `complaint_source_log.payload` 是入站原始报文留痕，脱它等于改留痕；本方案推荐**脱**，理由是 PII 合规优先于「原件不落地」，且留痕的**结构、键名、条数、哈希、行数**全部不动，审计能力不降级。
2. **占位样式 = 部分保留 `前3 + **** + 后4`**（如 `138****8000`）：可读、可判运营商号段、可跨行判同，**不可还原**，且脱敏后仍是 11 字符（长度不变 ⇒ 多出一条强断言）。
3. **不可逆**：不建任何号码映射表（映射表 = 换个地方继续存 PII，收益归零）；可逆性由**仓库外前像备份**承担，回滚是人工决策。

存量执行 = 一个 Node 驱动脚本（默认预演、`--apply` 才写、跑完自动断言）；增量入站**本批不做**（来源适配器已 `disabled`，无增量）；云上**不在云上跑脚本**，改为本机脱完后按批次④通道重镜像受影响 3 表，两侧以行级 CRC32 相等收口。

## 2. 唯一需要拍板的口径：入站留痕脱不脱

| 维度 | 不脱 `source_payload` / `complaint_source_log.payload`（只脱 `content`） | **脱（推荐）** |
| --- | --- | --- |
| 覆盖面 | 10 行「展示面」干净，**68 行原始号码仍在库** ⇒ 一次 `SELECT` 或一次全库备份外泄即全部落地 | 277 行 / 353 处一次性收口，断言可归零，验收是「全库零命中」这种可交付的硬指标 |
| 审计/留痕 | 原件逐字保真 | **只改号码子串**：表、行、列、键名、条数、`payload_hash`、时间线全不动；号码本身在留痕里也是**来源系统的经办人**联系方式，非诉求结论 |
| 幂等能力 | 不受影响 | **不受影响**：判重靠 `payload_hash`（`intakeService.ts:6` 的三支分支），本方案**不改哈希**（见 P-5），故留痕与哈希不再自洽，但判重逻辑在重新对接时是按「新报文算哈希 vs 库里存哈希」，届时口径需重议（§6） |
| 合规口径 | 仍是 D11 的「展示卫生 ≠ 合规级脱敏」 | 升级为「库内不留可还原手机号」，可对甲方/等保直接交代 |
| 不可逆代价 | 无 | 有：**原始号码在库内彻底消失**，若日后需要外呼回访，只能回来源系统取 |

**推荐：脱。** 唯一真正放弃的是「留痕原样」这一条，换来的是「全库命中归零」这个可验收结论；而外呼回访在本案场景里由来源系统（宜接就办）承担，本平台是分析平台，不具备回查诉求。

## 3. 占位规则

```
输入（假号）  上报人13800138000请回电
输出           上报人138****8000请回电
```

| 口径 | 取值 | 说明 |
| --- | --- | --- |
| 号码识别 | `(?<!\d)1[3-9]\d{9}(?!\d)`（JS）／`(^|[^0-9])1[3-9][0-9]{9}([^0-9]|$)`（MySQL 严格式） | **必须带非数字边界**：实测 `operation_audit_log` 的 8 行误配来自 **13 位毫秒时间戳**、`complaint_field_version.new_value` 的 1 行来自 **sha256 hex 摘要串**——两者都是长数字串里的 11 位子串，无边界就会脱错数据 |
| 掩码形状 | 前 3 + `****` + 后 4（11 → 11 字符，**长度不变**） | 前 3 位可判运营商号段；归属地需前 7 位 ⇒ 中段 4 位必须被掩，故该形状**不给归属地留信息** |
| 一处多号 | 同一列多处全部替换（`content` 10 行 10 处、`metadata` 58 行 72 处，实测每行 1～2 处） | 替换是全局式，非首次匹配 |
| 备选：全量 `[联系方式已隐去]` | 与 D11 既有 5 行标题样式一致、残存信息更少 | 代价：① 无法跨行判「是否同一经办人」（68 行里同一个人反复出现，判同是分析价值）；② 长度由 11 变 8，**「命中行长度不变」这条强断言失效**；③ 派生分析里看不出这行原本是号码还是别的信息 |

**推荐：部分保留式。** 若甲方在验收时明确「一位都不留」，则改全量式并重跑（脚本参数化 `--style=full`，两式对幂等与断言的差别只有长度那条）。

## 4. 可逆性

| 选项 | 本方案 | 理由 |
| --- | --- | --- |
| 建 `phone_mask_map` 映射表（可逆） | **不做** | 映射表就是 PII 换一张表继续存，脱敏收益归零；且它必须与脱敏同库同权限才可用 ⇒ 泄露面原封不动搬过去 |
| 号码加密（可逆、密钥外置） | **不做** | 需求里没有「按诉求回查经办人电话」的业务动作；加密只是把「脱敏」与「密钥管理」两个难题合成一个更难验收的难题 |
| 不可逆 + 仓库外前像备份 | **采用** | 回滚能力由 §8 的 `mysqldump` 前像承担（文件即真相），库内不留还原路径；回滚是人工决策，不是日常能力 |

## 5. 存量执行设计（一个脚本，先方案后执行）

脚本：`server/scripts/mask-phones.mjs`（与既有 `clear-seed-complaints.mjs`、`.dev-logs/backfill-*.mjs` **同风格**：`#!/usr/bin/env node`、`dotenv` 读 `server/.env`、`mysql2/promise`、口令只在内存、默认预演、显式占位符不依赖数组展开、日志与快照写**仓库外** `.dev-logs/`）。

```
node server/scripts/mask-phones.mjs                      # 预演：只 SELECT，零写入
node server/scripts/mask-phones.mjs --apply              # 真脱（含备份与断言）
node server/scripts/mask-phones.mjs --apply --sample 3   # 附加抽样：只报编号与占位样式
```

| 步 | 动作 | 关键设计 |
| --- | --- | --- |
| **S0 闸门** | 预演必须先通过：目标列命中数必须逐一等于 §1.1 的实测值（`68 / 204 / 5 / 10`），任一不符 ⇒ **中止不写** | 抄 `clear-seed-complaints.mjs` 的「目标集合逐字相符才动手」教训；防的是「库被别人改过」而非脚本 bug |
| **S1 备份** | `mysqldump --single-transaction --routines --triggers --events --hex-blob` 受影响 3 表（含结构）→ `D:\deepSeekHerness\zhuxinServer\backups\gqxq_service-pre-mask-<ts>.sql` | **仓库外**；含 PII ⇒ 不上云、不邮件、不入库；参数沿用 09-19 回填前备份定式 |
| **S2 前像快照（不含原文）** | 逐行落 `{表, id, 列, char_length, CRC32(concat(全列))}` → `.dev-logs/mask-preimage.json` | 用 **CRC32 而非明文**做标尺 ⇒ 快照文件本身零 PII，可以放在比备份更松的位置 |
| **S3 逐表 UPDATE** | 定位：`WHERE <col> REGEXP '(^|[^0-9])1[3-9][0-9]{9}([^0-9]|$)'`（JSON 列 `cast(... as char)`）；取值后**在 Node 侧掩码**；回写：`UPDATE <t> SET <col> = ? WHERE id = ?`，**按 id 升序、每表一个事务** | 为什么不用纯 SQL `REGEXP_REPLACE`：① MySQL 8.0.41 用的是 ICU，**不支持 lookahead/lookbehind**，两侧边界只能靠消耗式捕获，相邻两号的第二个有漏掩风险；② JSON 列要整体 `cast` 回写，转义面大；③ Node 侧可按 §1.2 的**精确路径**逐键处理，并天然支持 `(?<!\d)/(?!\d)`。SQL 侧只承担「定位」与「断言」两个角色，职责更清楚 |
| **S4 断言**（任一 FAIL ⇒ 回滚 + 保持现场，不改代码绕开） | 见下表 | 断言在库内算，不信脚本自述（沿用 `backfill-assert.mjs` 的口径） |
| **S5 幂等复跑** | 第二次 `--apply`：命中 0、变更 **0 行**、S2 的 CRC 与 S4 后全等 | 实测 `138****8000` 不再匹配宽松式（掩码后非连续数字）⇒ 天然幂等，无需额外状态位 |

**S4 断言清单：**

| 断言 | 期望 |
| --- | --- |
| 命中归零 | 4 个待改写位置（`complaint.content` / `complaint.source_payload` / `complaint_source_log.payload` / `complaint_field_version.old_value`）严格式命中全为 **0**；两个本就 0 的位置（`complaint.title`、`complaint_field_version.new_value`）复查**仍为 0**（防写歪） |
| 行数不变 | `complaint` **464** / `complaint_source_log` **1399** / `complaint_field_version` **43**；非目标表 `correction_item` **3712** / `sync_log` **929** / `operation_audit_log` **1917** 逐表不变（后三张**一行不碰**） |
| 变更行数 | 恰为 **68 / 204 / 5**（合计 277），多一条少一条都 FAIL |
| 非命中行逐字段不变 | 逐行 `CRC32(concat(全列))` 与 S2 前像比对：**非命中行 100% 相等**，命中行允许不等 |
| 命中行长度不变 | 命中行 `char_length` 前后相等（`11 → 11`，§3 形状换来的强断言） |
| JSON 仍可解析 | 命中行 `json_valid(source_payload) = 1`、`json_valid(payload) = 1` 全通过；`json_keys` 集合与 S2 一致（键不得增删） |
| 不动的东西 | `source_payload_hash` / `payload_hash` 全等（P-5）、`complaint_no` 全等、三轴业务状态校验和 `991751304380` 不变 |

| 一致性 | 本机 = 唯一权威，两侧**逐字**一致（批次④已确立此单向口径） | 两侧各自执行，同一份数据两次决策，边界差异/顺序差异都会造成静默漂移，且**没有标尺能证明它没发生** |
| 回滚 | 云上回滚 = 用本机 S1 前像再镜像一次（同通道） | 云上无本机式前像，回滚不对称 |
| 操作面 | 与批次④完全同形，可直接抄：`mysqldump --no-create-info --single-transaction --default-character-set=utf8mb4 --set-gtid-purged=OFF --complete-insert` → **管道直入** `docker exec -i gqxq-mysql mysql`，机上不落任何 dump 文件；口令走 `MYSQL_PWD` 就地取 | 需在云上再装 Node 依赖并把含 PII 的脚本产物落在第三方主机 |
| 范围 | 只 `TRUNCATE`＋`INSERT` **`complaint` / `complaint_source_log` / `complaint_field_version`** 三表（两侧行数原本逐字相等，批次④ CRC 全等，故这是「对齐」不是「新增」）；**红线表一行不碰**：`operation_audit_log` / `app_user` / `knex_migrations(_lock)` / `number_sequence` / `dict_*`；`correction_item`、`sync_log` 本次 0 命中 ⇒ **不重镜像** | — |

**断言方式（前例照抄批次④）：**

```sql
-- 两侧各跑一次，三个数必须两两相等（本机为基准；云上按实测记录）
select sum(crc32(concat_ws('#', id, ifnull(title,''), ifnull(content,''),
                           ifnull(cast(source_payload as char), ''), ifnull(source_payload_hash,'')))) from complaint;
select sum(crc32(concat_ws('#', id, payload_hash, ifnull(cast(payload as char), ''), result))) from complaint_source_log;
select sum(crc32(concat_ws('#', id, field_name, ifnull(old_value,''), ifnull(new_value,'')))) from complaint_field_version;
```

- 批次④旧校验和 `complaint 975490937465` / `complaint_source_log 3066590905396` / `complaint_field_version 74169710248` **必然改变**（这就是脱敏生效的证据），新值以本机脱敏后为基准，两侧相等即验收，并把新值记入知识库。
- 收尾：本机临时导出 SQL **灌完即 `rm -f` 并核实不存在**（含 PII，只允许存在于导出↔导入之间）；`GET /gqxq/api/v1/complaints` 仍 `total=464`、详情页正文显示 `138****8000` 样式。
