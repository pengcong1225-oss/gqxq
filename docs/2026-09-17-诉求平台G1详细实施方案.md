## 1. G1 目标与验收口径

### 1.1 目标（7 条，全部必须达成）

1. 诉求总账持久化到 MySQL，**服务重启不丢**。
2. `POST /api/v1/external/yijiejieban/appeal` 落库，唯一性由**数据库约束**保证，每次重传（含重复投递）都留痕。
3. 列表接口支持**服务端**分页与筛选；前端删除本地 Mock 数组。
4. 详情按 URL 中的 ID 或诉求编号查询；**任意行打开对应记录**，查不到就报"不存在"，不回退示例。
5. 仪表盘所有指标**来自数据库**；不可计算的指标返回 `null` 并在 UI 显示"—"，**禁止任何 `||` 兜底常量**。
6. 关键操作写入 `audit_log`（追加写，不可改）。
7. 交付三级验收证据（浏览器真实操作 + 数据库直查 + 服务重启后核对）与可执行门禁脚本。

### 1.2 验收口径（沿用交付纪律，G1 逐个落实）

| 纪律 | G1 的具体反制 |
| --- | --- |
| 禁止 Mock 回退 | 数据库不可用时接口返回 `500`，前端显示错误与重试；**不得**回落内存数组。见验收 A11 |
| 禁止无落库的成功 | 按钮点击必须产生可查询的持久化变化；不能落库的按钮改为**禁用 + 明确原因**，不得弹 `message.success` |
| 禁止跨请求随机 | 同一诉求两次查询返回相同结果；G1 后 `server/src` 内不得出现 `Math.random` / `randomItem` |
| 验收三级证据 | §8 的 A1–A11 每项都给出浏览器证据、SQL 证据、重启证据 |

## 2. 技术方案（D1 冻结）

### 2.1 选型表

| 关注点 | 选型 | 理由 | 备选（不推荐） |
| --- | --- | --- | --- |
| 语言 | TypeScript 5.x，编译目标 CommonJS | 与现有 Express 4 / `require` 生态零摩擦；ESM 会引入额外坑 | ESM（`"type":"module"`）|
| 运行时 | Node 24（本机 v24.19.0） | 已安装；内置 `node:test` 可省测试框架依赖 | 无 |
| 开发运行 | `tsx watch` | 无需构建即可热重启，启动快 | `ts-node`（较慢）、`nodemon+tsc` |
| 生产运行 | `tsc` 编译到 `dist/` 后 `node dist/index.js` | 产物可审计、启动不依赖编译器 | 直接 `tsx` 跑生产（不推荐） |
| Web 框架 | Express 4（沿用） | 现状即 Express，改造成本最低 | Fastify/Koa（重写无收益） |
| 数据库 | MySQL 8.0（本机 `MySQL80`） | 与 public-utility 同构，运维一致 | PostgreSQL（本机未装，且 G1–G6 不需要 PostGIS） |
| 驱动 | `mysql2/promise` 连接池 | 原生预处理语句（防注入）、性能好 | `mysql`（回调式，已过时） |
| 运行时 SQL 写法 | **手写参数化 SQL 集中在 repository 层** | 政务审计要求"数据 100% 来自数据库"且 SQL 可逐条复核；避免 ORM 隐式查询 | ORM（Prisma/TypeORM） |
| 迁移 | `knex` 作为迁移运行器，迁移体内写**原始 SQL** | 纯 npm 依赖、无需下载二进制（政务网离线友好）；DDL 仍是可 grep 的纯 SQL | `dbmate`（需 vendored 二进制）、自研 runner（重复造轮子且有风险） |
| 参数校验 | `zod` | 入站报文是跨系统契约，必须严格白名单校验 | 手写 if（易漏） |
| 鉴权 | `jsonwebtoken` + `bcryptjs` | 最小真实身份 | 继续 mock token（违反"留痕无真实身份"风险项） |
| 日志 | `morgan`（沿用）+ 结构化业务日志 | 现状即 morgan | pino（后续可换） |
| 测试 | `node:test` + `supertest` | Node 内置，零额外框架 | jest/vitest（重） |

> **关键取舍说明**：`knex` 只用于"建表/迁移"，业务查询一律走 `mysql2` 手写 SQL。这样既避免了自研迁移器的风险，又保证业务读写 SQL 显式可审。迁移文件内部用 `knex.raw()` 承载原始 SQL，因此 DDL 依然可以在仓库里被 grep 和 review。

### 2.4 数据库、账号与建库步骤（G1.0 前置）

数据库需由具备 DDL 权限的账号一次性创建。**本机 MySQL 的 root 口令未知，这是实施前的第一个阻塞项**（见 §11）。

```sql
-- 1) 建库（字符集固定 utf8mb4，排序规则 utf8mb4_0900_ai_ci）
CREATE DATABASE IF NOT EXISTS gqxq
  CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

-- 2) 迁移账号（建表/改表）
CREATE USER IF NOT EXISTS 'gqxq_migrator'@'127.0.0.1' IDENTIFIED BY '<强口令>';
GRANT ALTER, CREATE, DROP, INDEX, REFERENCES, SELECT, INSERT, UPDATE, DELETE
  ON gqxq.* TO 'gqxq_migrator'@'127.0.0.1';

-- 3) 应用账号（只做 DML，不给 DDL —— 便于审计"谁改了表结构"）
CREATE USER IF NOT EXISTS 'gqxq_app'@'127.0.0.1' IDENTIFIED BY '<强口令>';
GRANT SELECT, INSERT, UPDATE, DELETE ON gqxq.* TO 'gqxq_app'@'127.0.0.1';

-- 4) 测试库（供自动化测试使用，禁止指向 gqxq）
CREATE DATABASE IF NOT EXISTS gqxq_test
  CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
GRANT ALL PRIVILEGES ON gqxq_test.* TO 'gqxq_migrator'@'127.0.0.1';
GRANT SELECT, INSERT, UPDATE, DELETE ON gqxq_test.* TO 'gqxq_app'@'127.0.0.1';

FLUSH PRIVILEGES;
```

连接池关键配置（`src/db/pool.ts`）：

### 2.5 迁移工具用法

| 命令 | 作用 |
| --- | --- |
| `npm run migrate:latest` | `knex migrate:latest`，按文件名时间戳顺序执行 `migrations/` |
| `npm run migrate:rollback` | `knex migrate:down` 回退最近一批 |
| `npm run migrate:list` | 查看已应用/待应用 |
| `npm run migrate:make -- name` | 生成新迁移骨架 |

约定：
- 文件名 `YYYYMMDDHHmmss__描述.ts`，只允许**追加**，禁止修改已应用的迁移内容（knex 会校验）。
- 每个迁移必须**同时提供 `up` 与 `down`**；`down` 必须真的能删干净，并在本地验证过。
- 迁移内容用 `knex.raw()` 写原始 SQL，一句一条语句（`multipleStatements` 关闭）。

## 3. 数据模型

### 3.1 通用约定

| 项 | 约定 |
| --- | --- |
| 引擎/字符集 | `InnoDB` / `utf8mb4` / `utf8mb4_0900_ai_ci`（全表统一） |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT`，字段名一律 `id` |
| 时间列 | 一律 `DATETIME(3)`，**存 Asia/Shanghai 墙钟时间**（2026-09-17 实测修正：原方案写的"存 UTC"有误，见迁移设计 §3.1）；列名以 `_at` 结尾；API 返回 ISO-8601（`…Z`），前端本地化显示 |
| 业务日期 | "今日"等口径一律按 **Asia/Shanghai（+08:00）** 计算，不用服务器本地时区 |
| 布尔 | `TINYINT(1)`，0/1 |
| 枚举 | `VARCHAR` 存**大写英文码**（如 `WATER`），中文标签只在 `src/domain/enums.ts` 维护，API 同时返回 code 与 name |
| 金额/坐标 | `DECIMAL`，禁止 `FLOAT`（避免精度漂移） |
| 追加写表 | `complaint_source_log` / `complaint_field_version` / `audit_log` **只插入，不更新不删除**（应用层保证，另见 §3.4） |
| 命名 | 表名单数、小写下划线；索引 `idx_` 前缀；唯一键 `uk_` 前缀；外键 `fk_` 前缀 |

> **时区坑（务必按此实现）**：MySQL 在 Windows 上通常**未加载时区表**，`CONVERT_TZ(ts,'UTC','Asia/Shanghai')` 会返回 `NULL`。因此所有时区换算必须使用**数字偏移**：`CONVERT_TZ(received_at,'+00:00','+08:00')`。

### 3.2 表清单（G1）

| 表 | 类型 | 作用 | 关键约束 |
| --- | --- | --- | --- |
| `complaint` | 主表 | 诉求总账（来源快照 + 三条状态轴 + 办结/分析标记） | `UNIQUE(source_system, source_id)`、`UNIQUE(complaint_no)` |
| `complaint_source_log` | 追加写 | 每次外部投递留痕（含重复、被拒） | 无唯一约束（重复投递必须各留一条） |
| `complaint_field_version` | 追加写 | 必要字段变更的旧值/新值/来源/操作者 | 无 |
| `number_sequence` | 计数 | 按 `(seq_key, biz_date)` 原子发号 | `PRIMARY KEY(seq_key, biz_date)` |
| `audit_log` | 追加写 | 全量操作审计 | 无 |
| `app_user` | 主表 | 最小真实身份 | `UNIQUE(username)` |

```sql
  district_code            VARCHAR(32)      NULL,
  district_name            VARCHAR(64)      NULL,
  location_lng             DECIMAL(10,6)    NULL,
  location_lat             DECIMAL(10,6)    NULL,
  source_payload           JSON             NULL COMMENT '原始报文字节反序列化后的完整快照',
  source_payload_hash      CHAR(64)     NOT NULL COMMENT '规范化 JSON 的 sha256，幂等比对依据',
  source_reported_at       DATETIME(3)      NULL COMMENT '来源系统声明的诉求时间',
  source_updated_at        DATETIME(3)      NULL COMMENT '最近一次外部重传覆盖快照的时间',
  received_at              DATETIME(3)  NOT NULL COMMENT '本系统接收时间(UTC)',

  -- 规则引擎判定结果（可被外部重传重算覆盖）
  business_type            VARCHAR(16)  NOT NULL COMMENT 'WATER/GAS/LPG',
  complaint_type           VARCHAR(16)  NOT NULL COMMENT 'COMPLAINT/CONSULT/SUGGEST/REPORT',
  urgency_level            VARCHAR(16)  NOT NULL COMMENT 'NORMAL/URGENT/CRITICAL',
  is_sensitive             TINYINT(1)   NOT NULL DEFAULT 0,
  sensitive_keywords       JSON             NULL COMMENT '命中词数组',
  rule_confidence          DECIMAL(4,3)     NULL,
  rule_version             VARCHAR(32)      NULL COMMENT '规则版本，便于回查判定依据',

  -- 人工/自动纠偏（G5 写入；外部重传不得覆盖）
  corrected_address        VARCHAR(500)     NULL,
  correction_status        VARCHAR(16)  NOT NULL DEFAULT 'NONE' COMMENT 'NONE/PENDING/CORRECTED/FAILED',
  correction_confidence    DECIMAL(4,3)     NULL,

  -- 责任企业（G2 人工/自动匹配写入；G1 保持 NULL，前端显示"未匹配"）
  responsible_company_id   BIGINT UNSIGNED  NULL,
  responsible_company_name VARCHAR(200)     NULL,
  responsible_matched_at   DATETIME(3)      NULL,
```

### 3.5 诉求编号生成（`number_sequence`）

编号格式：`CS` + `yyyyMMdd` + 6 位零填充序号，例如 `CS20260917000001`。日期取 **Asia/Shanghai 的接收日**。

单条 SQL 原子发号（`src/db/sequence.ts`）：

```sql
INSERT INTO number_sequence (seq_key, biz_date, current_value)
VALUES (:seqKey, :bizDate, LAST_INSERT_ID(1))
ON DUPLICATE KEY UPDATE current_value = LAST_INSERT_ID(current_value + 1);

SELECT LAST_INSERT_ID() AS allocated;
```

要点：
- `LAST_INSERT_ID(expr)` 既写入又返回，插入与更新两条路径都会把分配值放入会话变量，无竞态。
- 发号必须在**与插入 `complaint` 同一事务**内，保证失败时序号不浪费也不跳号产生空洞记录。
- `biz_date` 由 Node 用 `+08:00` 计算后传入，不用 MySQL 的 `CURDATE()`（避免依赖服务器时区）。

### 3.6 搜索索引（迁移 V3，可选）

`keyword` 目前跨 `complaint_no / title / content / address_raw` 做 `LIKE '%…%'`，**无法命中 B-Tree 索引**。G1 数据量（数百至数万）可接受，但要写进已知限制。

推荐在 V3 增加中文全文索引（MySQL 8 内置 ngram 分词器）：

- 该迁移列为**可选**：若生产 MySQL 未启用 ngram，则跳过并在文档记录，G1 保持 `LIKE`。

### 3.8 seed 与"禁止 Mock 回退"的边界

**允许**：`server/scripts/seed.mjs` 在**开发/演示**环境向 MySQL 写入真实行（走 `intakeService`，带 `--count`、`--reset` 参数），数据来源是脚本，落库后与人工录入的数据完全同构。

## 4. 状态模型（D2 建议冻结）

> D2 原本阻塞 G2/G4/G5。G1 就需要把枚举与列**一次性建对**，否则 G2 必然改表。本节即为 **D2 的冻结提案**，请业主/负责人确认后写入 `server/src/domain/enums.ts` 作为唯一真源。

### 4.1 三条状态轴分离存储

| 状态轴 | 列名 | 谁能写 | G1 取值 |
| --- | --- | --- | --- |
| 来源事件状态（宜接就办，只读快照） | `source_event_status` | **只有 G6 来源适配器** | 恒为 `UNKNOWN` |
| 督办交办状态（gqxq 本系统） | `supervision_status` | complaintService / dispatchService | 恒为 `NONE`（G2 起推进） |
| 填报审批状态（public-utility 回传） | `reporting_status` | 只有 G4 回调处理器 | 恒为 `NOT_STARTED` |
| 本系统办结（独立标记） | `closed_in_system` + `closed_*` | closedService | 恒为 0 |

规则：
- **禁止**用一个 `status` 字段混装三条轴。落地计划 §1.2 的"交办列表随机状态"就是混装的后果。
- 页面按需组合展示；列表默认展示"督办状态"和"来源状态"，两者并列且都带口径说明。
- 服务端是状态推进的唯一入口，只接受 §4.3/§4.4 的合法转换，非法转换返回 `409 INVALID_STATE_TRANSITION`。

### 4.2 枚举定义（唯一真源 `server/src/domain/enums.ts`）

| --- | --- | --- |
| `NONE` | 未交办 | 否 |
| `PENDING_MATCH` | 待匹配单位 | 否 |

| `PUSHED` | 已推送待签收 | **是** |

### 4.3 督办状态合法转换（服务端唯一写入口）

| 从 | 到 | 触发条件 | 写入者 | 批次 |
| --- | --- | --- | --- | --- |
| `NONE` | `PENDING_MATCH` | 敏感命中且无责任企业 | 规则/人工 | G2 |
| `NONE` / `PENDING_MATCH` | `PENDING` | 责任企业已明确并创建交办 | 人工 | G2 |
| `PENDING` | `PUSHED` | 推送成功且拿到 task.id | 推送器 | G3 |
| `PUSHED` | `ACCEPTED` | 收到签收回执 | 回调 | G4 |
| `ACCEPTED` | `PROCESSING` | 收到 TASK_SUBMITTED | 回调 | G4 |
| `PROCESSING` | `RETURNED` | 收到 TASK_RETURNED | 回调 | G4 |
| `RETURNED` | `PROCESSING` | 企业补正后重新提交 | 回调 | G4 |
| `PROCESSING` | `COMPLETED` | 收到 TASK_APPROVED（最终同意） | 回调 | G4 |
| `PROCESSING` / `RETURNED` | `REJECTED` | 收到 TASK_REJECTED | 回调 | G4 |
| 任意"进行中" | `CANCELLED` | 受控撤销（必须填原因，写审计） | 人工 | G2 |
| `COMPLETED` / `REJECTED` | `ARCHIVED` | 归档（需已确认纠偏） | 人工 | G5 |

**显式禁止**：`COMPLETED` → `PENDING`（重复交办）、`CANCELLED` → 任意进行中（撤销不可复活）、任何状态 → `ACCEPTED` 以外的"跳过签收"。

### 4.4 填报审批状态合法转换

```
NOT_STARTED → PUSHED → ACCEPTED → SUBMITTED → APPROVED
                                   └→ RETURNED → SUBMITTED → …
                                   └→ REJECTED
```

关键规则（源自落地计划 §3.2 与设计文档 §4.3）：
- 事件类型只有 `TASK_SUBMITTED / TASK_APPROVED / TASK_REJECTED / TASK_RETURNED` 四种，结论只有 `AGREED / DISAGREED / RETURNED`。
- **"拟同意"不得越过纠偏直接进入分析库或本系统办结**：只有 `TASK_APPROVED` 且结论为 `AGREED` 才允许把 `reporting_status` 置为 `APPROVED`。
- 同一 `eventId` 重复投递只允许产生一次状态推进（`business_event` 唯一键，G4）。

### 4.5 本系统办结（`closed_in_system`）

- 与来源事件状态**完全解耦**：本系统办结**不得**回写 `source_event_status`。
- 必须同时记录 `closed_at` / `closed_by` / `closed_by_name` / `closed_basis`，四项缺一不可（应用层校验）。
- 触发条件（业主待确认，见 §11）未定前，G1 恒为 `0`；G5 落地时按确认结果实现。

### 4.6 外部重传字段保护清单（G1 核心安全设计）

外部重传可能发生在人工已经匹配单位、已经纠偏之后。**重传只允许覆盖来源快照，绝不能覆盖人工与业务结论。**

| 类别 | 字段 | 重传时 |
| --- | --- | --- |
| 来源快照（可覆盖） | `title, content, source_channel, address_raw, district_code, district_name, location_lng, location_lat` | 覆盖，并逐字段写 `complaint_field_version` |
| 规则结论（可重算覆盖） | `business_type, complaint_type, urgency_level, is_sensitive, sensitive_keywords, rule_confidence, rule_version` | 覆盖，并逐字段写版本 |
| 原始报文（覆盖） | `source_payload, source_payload_hash, source_reported_at, source_updated_at` | 覆盖（hash 用于幂等比对） |
| **人工/业务结论（保护）** | `responsible_company_id, responsible_company_name, responsible_matched_at, responsible_match_reason` | **不得覆盖**；命中则记录一条 `change_source='EXTERNAL_REDELIVERY'` 的 `complaint_field_version`（old=new，标记"重传试图改写被拒"）并写 `audit_log` |
| **纠偏结果（保护）** | `corrected_address, correction_status, correction_confidence` | 同上 |
| **状态轴（保护）** | `supervision_status, reporting_status, source_event_status` | 同上 |
| **办结/分析（保护）** | `closed_in_system, closed_at, closed_by, closed_by_name, closed_basis, analysis_included, analysis_record_id` | 同上 |

实现方式：`intakeService.applyRedelivery()` 只构造"可覆盖列"的 UPDATE 语句，保护列**不出现在 SQL 里**（而不是先写后判断），这样即使代码演错也不会覆盖。

## 5. 接口契约（G1）

### 5.1 统一响应封套与错误码

保持现有封套，因为 `packages/web-admin/src/api/request.ts` 的响应拦截器依赖 `data.code === 200` 并返回 `data.data`：

```json
{ "code": 200, "message": "success", "data": { } }
```

约定：
- 成功一律 HTTP 200 + `code:200`。
- 失败时 HTTP 状态码与 `code` **保持一致**（400/401/403/404/409/413/500），`data` 允许为 `null` 或承载 `fieldErrors`。
- 每个响应回显 `requestId`（放在 `data` 内或响应头 `X-Request-Id`），用于把前端报错与 `audit_log.request_id` 对上。
- 前端拦截器在 G1 需要小改：把 `code` 与 `fieldErrors` 附到 `Error` 对象上；`/auth/login` 的 401 不再触发跳转（见 §6.1）。

错误码表：

| HTTP | code | 含义 | 前端动作 |
| --- | --- | --- | --- |

字段规则（`zod` 严格校验）：

| 字段 | 必填 | 规则 | 缺省行为 |
| --- | --- | --- | --- |
| `sourceId` | 是（或 `appealId`） | 1–128 字符 | 无 → 400 |
| `title` | 是 | trim 后 1–500 | 无 → 400 |
| `content` | 否 | ≤ 20000 | `null` |
| `address` | 否 | ≤ 500 | `null` |
| `districtCode` / `districtName` | 否 | ≤ 32 / 64 | `null` |
| `source` | 否 | ≤ 64 | `null`（前端显示"未知来源"） |
| `businessType` / `complaintType` / `urgencyLevel` | 否 | 必须是 §4.2 的合法 code | 缺失 → 由规则引擎判定 |
| `longitude` / `latitude` | 否 | 必须成对；宜辖区范围 110.0–113.0 / 29.5–32.0 | **超范围不拒绝**：置 `null` 并在响应 `warnings` 与 `complaint_source_log.message` 中记明 |
| `createdAt` | 否 | 必须带时区偏移的 ISO-8601 | 缺失 → 取接收时间；格式错 → 400 |
| 未知字段 | — | 忽略但记入 `complaint_source_log.message` | — |

> 与 G3 的 public-utility 契约不同：本接口是**宜接就办 → gqxq** 的内部入站，G1 阶段暂用宽松字段集；G3 的 outbound 契约（15 字段白名单、HMAC）另行实现，两者不要混用。

**请求处理（必须单事务）**：

```text
1. 校验（zod）。失败 → 记 complaint_source_log(result=REJECTED) 后返回 400。
2. 规范化：canonicalJson(parsedPayload) → sha256 → payloadHash。
   canonicalJson 递归按键名排序，保证外部字段顺序变化不会误判为"内容变了"。
3. BEGIN
   a. SELECT ... FROM complaint WHERE source_system=? AND source_id=? FOR UPDATE
   b. 不存在：
      - complaint_no = nextNo('complaint', 上海日期)
      - 规则引擎判定 business_type / complaint_type / urgency_level / is_sensitive
      - INSERT complaint(...)
      - INSERT complaint_source_log(result=CREATED, complaint_id)
      - audit_log(EXTERNAL_APPEAL, CREATE)
   c. 存在，且 payload_hash 相同：
      - INSERT complaint_source_log(result=DUPLICATE_SAME, complaint_id)
      - 不改 complaint 任何列（幂等）
   d. 存在，且 payload_hash 不同：
      - 按 §4.6 只更新"可覆盖列"；对每个真正变化的字段写 complaint_field_version
      - INSERT complaint_source_log(result=UPDATED, complaint_id, message=变化字段列表)
      - audit_log(EXTERNAL_APPEAL, REDELIVERY)
   COMMIT
4. 并发兜底：步骤 3b 的两条并发插入会有一条命中 uk_complaint_source 报 ER_DUP_ENTRY；
   捕获后重读该行，按 3c/3d 重新判定。**唯一性由数据库裁决，不靠应用层 SELECT 判断。**
```

**响应**：

```json

  "data": { "result": "CREATED", "duplicate": false, "complaintId": 201,
            "complaintNo": "CS20260917000201", "changedFields": [], "warnings": [] } }
```

```json

  "data": { "result": "DUPLICATE_SAME", "duplicate": true, "complaintId": 201,
```

```json

  "data": { "result": "UPDATED", "duplicate": false, "complaintId": 201,
            "complaintNo": "CS20260917000201",
```

**关键点**：`"duplicate": true/false` 与 `"result"` 都必须落库可查（`complaint_source_log.result`），不能只体现在响应里。

```ts
const request = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL ?? '/api/v1',
  timeout: 15000,
});

request.interceptors.response.use(
  (response) => {
    const { data } = response;
    if (data.code !== 200) {
      const err = new Error(data.message || 'API Error') as any;
      err.code = data.code;
      err.fieldErrors = data.data?.fieldErrors;
      return Promise.reject(err);
    }
    return data.data;
  },
  (error) => {
    const status = error.response?.status;
    const body = error.response?.data;
    const err = new Error(body?.message || error.message) as any;
    err.code = body?.code ?? status;
    err.fieldErrors = body?.data?.fieldErrors;
    err.status = status;
    // 登录接口自身的 401 不跳转，交给页面提示
    if (status === 401 && !error.config?.url?.includes('/auth/login')) {
      localStorage.removeItem('token');
      window.location.href = '/login';
    }
    return Promise.reject(err);
  }
);
```

## 7. 最小真实身份（G1.6，可裁剪）

落地计划风险表指出"鉴权仍是 mock token → 留痕无真实身份"。G1 的 `audit_log` 必须有真实 `actor_id`，否则审计等于没做。因此本方案把最小真实身份纳入 G1：

| 项 | 做法 |
| --- | --- |
| 存储 | `app_user` 表，口令 `bcryptjs` 加盐哈希（cost 10） |
| 令牌 | JWT，HS256，`GQXQ_JWT_SECRET`，TTL `GQXQ_JWT_TTL_SECONDS`（默认 8h） |
| 中间件 | `requireAuth` 保护除 `/health`、`/auth/login`、`/external/*` 外的全部 `/api/v1` |
| 初始化 | 首次 `seed` 用 `GQXQ_BOOTSTRAP_ADMIN_PASSWORD` 创建 admin；**未配置则拒绝创建并打印告警，绝不使用硬编码默认口令** |
| 审计联动 | 所有受保护接口把 `req.user.id/realName` 写入 `audit_log.actor_id/actor_name` |
| 权限 | `roles/permissions` 先落库（`['*']` 管理员），**G1 不做细粒度鉴权**，只做认证 |

若业主要求 G1 只做总账、身份延后，则 **G1.6 可整体裁剪**，但必须同时接受"G1 期间 `audit_log.actor_name` 只能记 `system`，审计不完整"这一明确缺口，并把它写成 G2 的强制前置。

## 12. 结论

1. **D1 已定**：Node/Express → TypeScript + MySQL 8 + knex 迁移；本机 MySQL 8 就绪，方案可立即落地。
2. **G0 已完成**：`baseline-20260917` 提供可回退基线，工作树干净，未推送远端。
3. **G1 的 6 个技术难点都已在本文给出可直接实现的规格**：唯一性交给数据库、幂等按 payload hash 三分支、人工字段保护清单、仪表盘零兜底、状态三轴与 D2 枚举、三级验收证据与门禁脚本。
4. **G1 的真实前置只有一个**：MySQL 凭证与建库（§11 第 1 项）。拿到后即可从 G1.0 开工，预计 **6.0 人日**（裁剪 G1.6 则 5.5 人日）。
5. 落地计划 §2 的 D3–D6 不影响 G1，可在 G1 实施期间并行推进；其中 D2 建议直接采用 §4 的枚举并冻结。
