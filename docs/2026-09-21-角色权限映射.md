## 1. 三档角色定义（存 `app_user.roles` json，一人一档）

| 角色 | 定位 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| `admin` | 系统管理员 | 全部端点（含用户管理、字典管理） | — |
| `handler` | 业务经办 | 全部读 + 业务写（交办/受控撤销/推送/重推/归档/纠偏生成与确认/归库/回填类同步/办结） | 用户管理、字典管理、任何**未在本表声明**的端点 |
| `readonly` | 只读 | 全部读端点 | **任何非 GET**（硬性不变量，见 §4）、用户管理、字典管理 |

`admin` 在代码里是全量放行档（`isAllowed` 第一判据），因此「新增端点忘记声明」
的后果只落在 handler / readonly 身上 —— 他们拿不到未声明端点，这正是默认拒绝要的效果。

## 4. 默认拒绝与 401/403 语义（交付纪律）

1. **默认拒绝**：`isAllowed()` 在 `ROLE_POLICY` 里找不到匹配条目时，等价于
   `roles: ['admin']`。新增路由的作者必须显式加一条策略，否则只有 admin 能用——
   出现"功能上线了但经办点不动"时，第一查这里是漏了策略行，不是 RBAC 坏了。
2. **只读的硬不变量**：非 GET 请求在任何判定之前先把 `readonly` 剔除，
   即使有人误写 `roles: ['readonly']` 的 POST 策略也不会放开。
3. **401 / 403 分开**：缺 Bearer、令牌无效/过期、载荷缺字段、**令牌有效但账号已被禁用或已查不到**
   → `401 UNAUTHENTICATED`（`requireAuth`，第 9 条）；已认证但角色不足 → `403 FORBIDDEN`
   「无权限，请联系管理员」。403 **不跳登录页**（前端拦截器只对 401 跳）。
4. **403 也审计到人**：判定拒绝时写 `operation_audit_log`
   （`action='ACCESS_DENIED'`，`user_id` 为真实登录者，detail 记 method/path/依据）。
5. **审计到人不靠硬编码**：所有写路径的 `ctxOf(req)` 取 `req.user.id / req.user.username`
   （由 `requireAuth` 用 JWT `sub` 回库取到的真实身份注入），本批复核确认没有任何一处写死 admin；
   用户管理自身的写操作同样走 `insertAudit`（`USER_CREATE` / `USER_UPDATE`）。
6. **不用 `permissions` 列做鉴权**：本批是角色级 RBAC，`app_user.permissions`
   保留给未来的权限树，不参与判定（避免两套真源）。
7. **"到人"只管平台侧发起的写**：`verify:rbac` 实测确认，机器通道（§2 的 P3 入站）写的
   `INTAKE_CREATE` 仍是 `user_id = NULL` —— 它没有平台账号可记，硬填一个 admin 反而是造假。
   判据是"凡是登录者触发的写，user_id 必须是登录者本人"，不是"所有审计都有 user_id"。
8. **登录层的 400 与 401 先于 403**（本批未改，写下来免得被当成 RBAC 的锅）：
   口令为空/超长 → `400 VALIDATION_FAILED`（契约层，连库都不查）；口令错、账号被禁用 →
   `401 UNAUTHENTICATED`；只有"令牌有效但角色不够"才是 `403 FORBIDDEN`。
9. **令牌只证明身份，档位以库为准**（收尾修复；`verify:rbac` 的 RBAC-09 断言）：
   `requireAuth` 验签之后，用 `sub` 回 `app_user` 点查一次 `roles` 与 `status`，
   `req.user` 用查到的值注入（**不取令牌里的 `roles` 声明**）。
   原语只验签名时，`PATCH /users` 的「禁用」「降级」要等对方那枚 TTL 8 小时的令牌
   自然过期才生效 —— 期间被降级的 admin 仍能进 `/users`，而策略表的默认拒绝拦不住它
   （它拒的是"角色不够的人"，老令牌报的是"我还够"）。代价是每个受保护请求多一次
   主键点查；收益是治理动作即时生效，且 `user_id` 反查不到人时宁可 401 也不放行。
   库读失败同样不透支判定：错误直送 `errorHandler`，绝不回退到令牌里的旧角色。

## 5. 遗留 / 需裁定

- 操作日志页（`/system/users` 旧 Mock 的"操作日志"页签）需要
  `GET /audit-logs`（读 `operation_audit_log`）才有真数据，本批不做，页签已撤下而不是留假数据。
- 角色目前是**单档**（`roles` 数组里一个值）。一人多档（如 admin+handler）在实现上支持，
  但 UI 与建号接口按单档给；是否需要多档叠加待业务方裁定。
- 云端（部署批 #36）真实业务账号需要业务方给名单与口令分发方式；本批只在本机建
  `test_handler_*` / `test_readonly_*` 测试账号。

## 6. 怎么验（`npm run verify:rbac`）

`server/scripts/verify-rbac.mjs` 两种模式，**串行**跑：

| 模式 | 命令 | 打谁 | 断言 |
| --- | --- | --- | --- |
| A 全量 | `npm run verify:rbac` | 自起一次性实例（`127.0.0.1:3340` + `GQXQ_TEST_DB_NAME`） | RBAC-01…13：登录带 role、策略表↔本文档逐条 45=45、默认拒绝、readonly 硬不变量、20 条写端点逐个 403 且零副作用、业务写审计到人、`/users` CRUD + 防呆（撞库 409 / 列宽 400 / 无 DELETE / 最后一个 admin / **禁用与降级即时回收已签发令牌**）、401 与 403 分开、机器端点未被波及、探针数据归零 |
| B 抽查 | `npm run verify:rbac:live`（= `--live=http://127.0.0.1:3100/api/v1 --db=gqxq_service`） | 已在跑的 3100 | RBAC-L0…L5：三档登录取令牌、6 端点矩阵、`/users` 仅 admin、401/403 语义、审计回读、最后一个 admin 自禁 409 |

模式 B 刻意只探测 **6 个端点**（3 读 + 2 写 + 1 管理面），不像模式 A 那样把 45 条策略全
sweep 一遍：它可能打**真实库**，而每次 readonly 越权都会落一条 `ACCESS_DENIED` 审计。
模式 B 全程不写业务数据——写探针一律用会被 RBAC 拦掉的角色、或不存在的业务键。
向真实库建测试账号要同时给 `--provision --allow-main-write` 两道闸，本批供 #36 部署后对照的
`test_handler_01` / `test_readonly_01` 就是这么落在 `gqxq_service` 的（口令只进 env，不落文档）。
