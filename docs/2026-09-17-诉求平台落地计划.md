## 0. 交付纪律（贯穿全部批次）

以下四条是对现有实现问题的直接反制，每个批次都要检查：

1. **禁止 Mock 回退。** 接口失败、数据为空时，页面必须显示真实空态或错误与重试，不得回落到本地数组、`||` 默认值或"操作成功"提示。参考 `server/src/index.js:124-134` 的 `todayTotal || 1247` 是典型反例。
2. **禁止无落库的成功。** 任何按钮点击必须产生可查询的持久化状态变化。参考 `server/src/index.js:328-344`（新建交办不落库）是典型反例。
3. **禁止跨请求随机。** 同一记录两次查询必须返回相同状态。参考 `server/src/index.js:310-326`（交办列表用 `randomItem()` 现场生成）是典型反例。
4. **验收三级证据。** 单个接口返回 `200` 不算通过。每项验收必须同时具备：浏览器真实操作、数据库直查、**服务重启后状态核对**。

### 1.2 文档漏报的四条缺陷（本计划必须修掉）

1. **交办实体不存在。** `GET /api/v1/dispatch/orders`（`server/src/index.js:310-326`）不是查表，而是把敏感诉求现场 map 一遍，`dispatchType/triggerType/status/syncStatus/externalStatus` 全部 `randomItem()` 现算。且 `id: i + 1` 是**数组下标**，导致 `POST /dispatch/orders/3/push` 两次请求可能指向不同诉求。推送/归档无法对应稳定记录。

## 3. 跨系统契约实现规格

本节是 **gqxq 侧的权威实现规格**，直接摘自对方已通过的测试代码。按此实现可一次性通过联调。

### 3.1 入站：gqxq → public-utility 创建填报任务

**请求**

```text
POST /api/integrations/gqxq/tasks
Content-Type: application/json
X-PU-Key-Id:    <已登记凭证 keyId>
X-PU-Timestamp: <Unix 秒>
X-PU-Nonce:     <每次请求唯一>
X-PU-Signature: <小写 hex>
```

**签名（`HmacRequestAuthenticator`）**

```text
canonical = "v1" + "\n" + METHOD(大写) + "\n" + path + "\n" + timestamp + "\n" + nonce + "\n" + lowercaseHexSha256(原始 body 字节)
signature = lowercaseHex(HMAC-SHA256(key = secret 的 UTF-8 字节, message = canonical 的 UTF-8 字节))
```

关键点：
- `path` 必须是 `/api/integrations/gqxq/tasks`（`getRequestURI` 结果，不带 query）。
- `bodySha256` 必须是对**实际发送的原始字节**求 SHA-256，不能是重新序列化后的 JSON。**必须序列化一次、缓存字节、用它签名并发送**，否则必然验签失败。
- 时间戳容差 **±300 秒**（`IntegrationSignatureHttpTest:150`）。
- `path` 中的 `{app}`、body 的 `sourceAppCode`、凭证身份三者必须一致。

**请求体（严格白名单，多一个字段即 422）**

允许字段仅 15 个：`sourceAppCode, sourceBusinessId, requestId, sceneCode, templateCode, templateVersion, title, deadline, focusFlag, enterpriseSubjects, prefilledData, approvalDefinitionCode, approvalDefinitionVersion, callbackPolicy, metadata`。
嵌套白名单：`enterpriseSubjects[]` 仅 `subjectCode, subjectName, contactUserCode, contactUserName`；`callbackPolicy` 仅 `subscriptionCode, deliveryRequired`。

> **注意：不要发送 `organizationCode`。** 它在服务端 DTO（`IntegrationTaskRequest:32`）中存在，但**不在验签过滤器的白名单里**，发送会被 422 拒绝。这是对方 DTO 与白名单的漂移，gqxq 侧规避，同时向对方提缺陷。

其他约束：body ≤ **1 MiB**；必须是单个 JSON 对象，尾随内容会被拒；`deadline` 必须是**带时区的** ISO-8601（`OffsetDateTime.parse`，如 `2026-09-20T18:00:00+08:00`）；`enterpriseSubjects` 至少 1 项。

**场景码语义（由 `sceneCode` 决定）**

| sceneCode | 结果 |
| --- | --- |
| `GQXQ_SENSITIVE_DISPATCH` | `created=true`，`disposition="SENSITIVE_ASSIGNMENT"`，返回 `task` |
| `GQXQ_ORDINARY_ARCHIVE` | `created=false`，`disposition="ARCHIVE_ONLY_IN_GQXQ"`，`task` 不存在 |

即**普通诉求不应调用此接口**，由 gqxq 自行归库；接口只在敏感交办时调用。

**参考载荷**（对方测试 fixture，可直接作为联调样例）

```json
{
  "sourceAppCode": "gqxq",
  "sourceBusinessId": "CPL202609140001",
  "requestId": "ASSIGN202609140001",
  "sceneCode": "GQXQ_SENSITIVE_DISPATCH",
  "templateCode": "GQXQ_SENSITIVE_DISPATCH",
  "templateVersion": 1,
  "title": "沿江大道停水事件敏感交办",
  "deadline": "2026-09-20T18:00:00+08:00",
  "focusFlag": true,
  "enterpriseSubjects": [
    { "subjectCode": "ENT-WATER-001", "subjectName": "宜昌市供水总公司",
      "contactUserCode": "user-water-001", "contactUserName": "供水值班员" }
  ],
  "prefilledData": {
    "complaintNo": "CS202609140001",
    "sourceEventNo": "YJJB202609140001",

  "metadata": { "focusLabel": "重点关注", "eventSource": "宜接就办状态同步预留" }
}
```

**幂等与重试语义**（必须在 gqxq 侧正确实现）

| 情形 | 对方行为 | gqxq 应对 |
| --- | --- | --- |
| 同 `requestId` + **完全相同** body | 200，返回**首次**的 `task.id` | 视为成功，更新本地 `taskId` |
| 同 `requestId` + 不同 body | **409 CONFLICT** | **不可自动重试**，转人工核对 |
| 同 `nonce`（票据重放） | **409 INTEGRATION_REPLAY** | **换新 nonce + 新时间戳**重试 |
| 网络超时 | 结果未知 | 用**同 requestId、同 body、新 nonce、新时间戳**重试，不得新建交办 |

**错误码处置表**

| HTTP | code | 含义 | gqxq 动作 |
| --- | --- | --- | --- |
| 401 | `INTEGRATION_AUTHENTICATION_FAILED` | 签名/时间戳/路径/app 不符 | 检查凭证与时钟偏差；不盲目重试 |
| 409 | `INTEGRATION_REPLAY` | nonce 已用 | 换 nonce 重试 |
| 409 | `CONFLICT` | requestId 载荷冲突 | 停发，人工介入 |
| 413 | `PAYLOAD_TOO_LARGE` | body > 1 MiB | 精简 `prefilledData`/`metadata` |
| 422 | `VALIDATION_FAILED` | 校验失败（含未知字段） | 修正后重试，记录 `fieldErrors` |

### 3.2 出站：public-utility → gqxq 回传结果事件

gqxq 必须**对外提供**一个回调端点接收 `business result event`。

**请求头**（`HttpCallbackTransport.java:106-110`）

```text
X-Public-Utility-Key-Id
X-Public-Utility-Key-Version
X-Public-Utility-Timestamp
X-Public-Utility-Event-Id
X-Public-Utility-Signature
```

**签名算法与入站不同**（`CallbackSignatureService.sign(secret, epochSeconds, exactBody)`）

```text
canonical = epochSeconds + "\n" + lowercaseHexSha256(原始 body 字节)
signature = lowercaseHex(HMAC-SHA256(key = secret 原始字节, message = canonical))
```

> 注意：**没有** `v1`、没有 method/path/nonce。切勿复用入站实现。

**ACK 语义（高危陷阱）**

- 订阅上配置 `ackMode` 为 `NONE` 或 `BODY`。
- 若为 `BODY`，gqxq 的**响应体必须逐字节等于配置的 `ackValue`**。
- ACK 不匹配会判定为 `CALLBACK_ACK_INVALID`，且该错误**不可重试**。ACK 配错等于事件被永久丢弃。
- 可重试状态码会按 `Retry-After` 重试；永久状态码不重试。
- 事件 ID 是投递幂等键：gqxq 侧必须按 `eventId` 去重，重复投递返回**同一 ACK**。

**事件载荷**：见对方 `docs/contracts/public-utility-result-event.json`。`eventType` 枚举仅 `TASK_SUBMITTED / TASK_APPROVED / TASK_REJECTED / TASK_RETURNED`；`approvalConclusion` 枚举 `AGREED / DISAGREED / RETURNED`。

> **契约缺口（需双方确认）**：`TASK_SUBMITTED` 不能表达"企业签收"。而 gqxq 设计文档 §4.3 要求"签收、提交、退回、最终审批分别可追踪"。签收是走独立订阅事件，还是靠任务创建响应回执？**G3 启动前必须书面确认。**

## 4. 数据模型（建议）

三条状态轴**分开存储**，页面组合展示，服务端按允许转换推进：

- **来源事件状态**（宜接就办，只读快照）
- **督办交办状态**（gqxq 本系统）
- **填报审批状态**（public-utility 回传）
- 另有独立的 **"本系统办结"** 标记（含确认人、时间、依据），不得据此修改来源事件状态

| 表 | 关键约束 | 说明 |
| --- | --- | --- |
| `complaint` | `UNIQUE(source_system, source_id)` | 诉求总账；保存来源快照、接收时间、分类、责任企业、敏感命中、三轴状态、分析入库标记 |
| `complaint_source_log` | 追加写 | 每次外部重传留痕（含重复投递） |
| `complaint_field_version` | 追加写 | 必要字段变更的旧值/新值/操作者/时间 |
| `complaint_assignment` | 追加写 | 手/自动匹配责任单位，保存前后值、原因、操作者 |
| `sensitive_rule` / `sensitive_rule_version` / `sensitive_hit` | `sensitive_hit` 存命中证据 | 词条、范围、版本、审核结果 |
| `dispatch_order` | **一个诉求同一轮只能有一条有效交办** | 交办编号、诉求 ID、企业主体、触发类型、原因、模板/审批版本、要求、截止、请求号、填报任务 ID、推送与回传状态 |
| `dispatch_request_log` | 按 `request_id` 去重 | 推送原始请求/响应/ACK/失败原因/重试次数 |
| `business_event` | `UNIQUE(event_id)` | 回传事件原文 + 处理结果，幂等依据 |
| `approval_trace` | 追加写 | 签收/提交/退回/最终审批轨迹 |
| `correction_item` | 逐字段一行 | 旧值/新值/依据/确认人/时间 |
| `analysis_record` | 由已确认纠偏生成 | 分析库 |
| `report_todo` | 关联 analysis_record | 待查报告入口 |
| `audit_log` | 追加写 | 全量操作审计 |

**"唯一交办"的落库做法**（G2 核心）：MySQL 不支持部分唯一索引，用生成列实现：

```sql
ALTER TABLE dispatch_order
  ADD COLUMN active_complaint_id BIGINT
    GENERATED ALWAYS AS (IF(status IN ('PENDING','PUSHED','ACCEPTED','PROCESSING','RETURNED'), complaint_id, NULL)) STORED,
  ADD UNIQUE KEY uk_active_dispatch (active_complaint_id);
```

这样"重复点击、重试、刷新不得生成第二条有效交办"由**数据库约束**保证，而不是靠应用层判断。

| 任务 | 1. **前置**：确认对方已合并分支（D3）并登记 app=`gqxq`、模板 `GQXQ_SENSITIVE_DISPATCH` v1、审批定义 `GQXQ_SUPERVISION_APPROVAL` v1、回调订阅 `GQXQ_TASK_RESULT`（D4）；2. 取得 keyId/secret 凭证并安全存储；3. 按 **3.1 节**实现签名客户端（务必缓存序列化字节）；4. 交办 → 创建任务，`requestId`=交办唯一请求号；5. 持久化 `taskId`+ACK 到 `dispatch_request_log`；6. 实现错误码处置与重试策略；7. 确认签收回执契约（3.2 节缺口） |
| 验收 | ① **同一 requestId 多次推送，两系统都只有一个任务**；② 篡改 body 返回 401；③ 重用 nonce 返回 409 且换新 nonce 可成功；④ 超时重试不产生第二条任务；⑤ 响应 `task.id` 落库可查 |
| 依赖 | G2、D3、D4 |

### G4 回传闭环

| 项 | 内容 |
| --- | --- |
| 目标 | 企业处置结果与审批结论可靠回传，幂等无重复 |
| 任务 | 1. 按 **3.2 节**提供回调端点，实现**独立的**回调验签；2. 建 `business_event`（`UNIQUE(event_id)`）与 `approval_trace`；3. 按 `eventId` 幂等，重复投递返回同一 ACK；4. **精确配置 ACK 响应体**（BODY 模式必须逐字节相同，否则事件永久丢弃）；5. 事件推进本地督办/审批状态，`拟同意` 不落最终；6. 交办详情展示企业处置结果、审批轨迹、附件元数据；7. 附件下载与存证（D6） |
| 验收 | ① 退回重提 + 最终同意后，诉求与交办页面显示一致结果；② 重复回传无重复业务结果；③ ACK 不匹配场景可复现并已修正；④ 全链路 `eventId` 可反查 |
| 依赖 | G3 |

### G5 回传后流程

| 项 | 内容 |
| --- | --- |
| 目标 | 最终回传 → 纠偏 → 分析库 → 待查报告 |
| 任务 | 1. 最终回传生成纠偏待办（企业名称/归属、地址、分类、坐标、摘要、企业处置结果逐项）；2. 建 `correction_item`，保存旧值/新值/依据/操作者；3. **纠偏确认后才写 `analysis_record`**；4. 建 `report_todo`，可下钻回诉求/交办/表单/审批/纠偏；5. 独立的"本系统办结"状态与确认留痕；6. 前端 `AddressCorrection`、`DispatchArchive`、`ReportView` 接真实数据，去掉 Mock 与 `setTimeout` 假成功 |
| 验收 | ① **未纠偏不得进入分析库**（可测试的负向用例）；② 从待查报告可追溯全链路；③ 纠偏改动可回查旧值 |
| 依赖 | G4、D2 |

## 6. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 无版本基线 | 改造不可回退 | **G0 强制前置** |
| 联调依赖在对方未合并分支 | G3 无限期阻塞 | D3 上升为项目级依赖，书面确认合并时间；同时按 3.1 节独立开发并用对方 fixture 做本地桩 |
| ACK 配置错误导致事件永久丢弃 | 数据静默丢失 | G4 必须做 ACK 不匹配的负向用例；上线前核对订阅 `ackMode`/`ackValue` |
| 仪表盘假数据被当成真实指标 | 上线后业主发现 | G1 列为强制项并做代码检索门禁 |
| `organizationCode` 白名单漂移 | 联调 422 | gqxq 侧不发送；向对方提缺陷 |
| 鉴权仍是 mock token | 留痕无真实身份 | G1 一并落地最小真实身份，或明确 G2 前补齐 |
| 状态机未冻结就开发 | 返工 | D2 在 G2 前冻结 |

## 7. 待业主/对方确认项（不阻塞 G1）

1. 自动敏感词命中但**无交办单位**时，是否保留在总账"待匹配"（设计文档 §2 建议，未确认）。
2. 敏感词命中是否自动推送，还是必须人工复核。
3. 多企业责任的拆分口径（契约 `enterpriseSubjects` 已支持多主体，待定的是一个诉求拆几条交办）。
4. "本系统办结"的触发条件。
5. 未交办归库诉求是否纳入同一分析口径（直接影响分析库表结构）。
6. "待查报告"的形成、审批与发布规则。
7. **签收回执走独立事件还是任务创建响应**（3.2 节缺口，阻塞 G3）。
8. 回传附件是否由 gqxq 下载存证。
9. `organizationCode` 是否应纳入验签白名单。
