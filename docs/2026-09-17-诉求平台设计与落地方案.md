# 诉求平台完整设计、现状与落地方案

> 核对日期：2026-09-17。本文依据本次会话确认的业务流程、`gqxq` 当前工作树和同级 `public-utility` 的权威设计整理。本文是实施方案，不代表功能已经交付。

## 1. 业务边界与用语

`gqxq` 是行政机构的诉求汇聚、重点关注和督办线。事件的实际处置仍在“宜接就办”；`gqxq` 后续通过预留适配器读取其状态，不在本期等待真实接口联调。`public-utility` 是独立的企业填报和主管单位审批系统，承接重点关注的二次提醒与反馈。普通诉求不需要交办时直接归库。

- 菜单和业务名称保留“敏感交办”“本系统办结”。统一称“企业处置结果”。
- “企业处置结果”是本次督办填报反馈；“宜接就办处置状态”是来源事件状态。两者分别存储和展示，不互相覆盖。
- 诉求管理列表是所有已接收诉求的总账。进入“敏感交办”表示已经产生督办交办记录，不在该列表中再做一次人工交办。
- 当前各业务系统独立登录；统一登录属于后续议题。

## 2. 严格按诉求流程图设计的主流程

```text
市民投诉 → 宜接就办 → 诉求接收（诉求管理：全部接收诉求的总账）
                         → 手动匹配/调整交办单位，敏感词自动识别
                         → 是否敏感交办（也允许在总账中人工决定）
                            ├─ 否：归库，不推送企业、不在本系统处置事件
                            └─ 是：基于原诉求生成唯一交办记录
                                   → 进入敏感交办列表（此时已完成交办决定）
                                   → 推送交办单位签收（同级 public-utility）
                                   → 企业 Web 填报“企业处置结果”
                                   → 主管单位钉钉移动审批
                                   → 同步/回传处理结果
                                   → 诉求信息纠偏调整
                                   → 纠偏后进入分析库
                                   → 待查报告
```

流程图中的“市民投诉、宜接就办”是事件来源与实际处置线；“诉求接收”及其后续节点才是 `gqxq` 的督办线。本期宜接就办真实接口尚未对接，保留来源 ID、接收和只读状态适配器，不把模拟状态当成真实处置进度。“本系统办结”保持现有名称，作为本系统独立状态展示，不替代流程图中的“待查报告”，也不改写宜接就办的事件办结状态。

| 流程图节点 | 所属页面/系统 | 应产生的业务结果 |
| --- | --- | --- |
| 诉求接收 | `gqxq` 诉求管理 | 所有已接收诉求进入同一总账，去重并保存来源 ID、原始内容和接收轨迹；详情打开对应的真实诉求 |
| 手动匹配交办单位 | `gqxq` 诉求管理 | 操作员在原诉求上匹配或调整责任企业/单位，保存前后值、原因和操作者；自动敏感词识别不能取消人工分配能力 |
| 是否敏感交办 | `gqxq` 诉求管理 | 自动敏感词或人工选择决定分流；不需交办的诉求直接归库；需交办的在原诉求下只创建一次交办记录 |
| 进入敏感交办列表 | `gqxq` 敏感交办 | 只展示已产生的交办记录及进度，不能在此脱离诉求再次新建/再次交办 |
| 推送交办单位签收 | `gqxq` → `public-utility` | 以已发布表单模板创建任务，记录发送、对方 ACK、任务 ID、失败与重试；交办单位在填报系统签收 |
| 同步/回传处理结果 | `public-utility` → `gqxq` | 企业 Web 填报“企业处置结果”，主管单位按配置的审批人和意见在钉钉审批；签收、提交、退回、最终审批分别回传并留痕 |
| 诉求信息纠偏调整 | `gqxq` 纠偏待办 | 最终结果回传后核对责任单位、地址、分类、摘要及结果等信息，保存旧值、新值、依据和确认人 |
| 纠偏后进入分析库 | `gqxq` 分析库 | 只将满足纠偏规则的交办诉求写入分析数据，保留可回查的诉求、交办、表单和审批关联 |
| 待查报告 | `gqxq` 报告待办 | 基于分析库形成待查记录/报告入口，能从报告反查原诉求和全程轨迹；报告审批与发布规则待业务方确认 |

自动敏感词的作用是帮助**在总账完成分流**，不是在“敏感交办”里再发起一次交办。建议只有交办单位已明确时才生成正式交办记录并进入该列表；命中词但缺单位的诉求保留在总账“待匹配”，提示操作员处理。这一例外规则尚待业主确认。人工分配单位、人工敏感标记、误报归库均在总账操作并留痕；重复点击、重试和页面刷新不得生成第二条有效交办。

“敏感交办”页的动作仅限查看、推送/失败重试、催办、签收与反馈跟踪、回传核对、受控撤销和归档。审批退回后在原交办下形成企业补正轮次，不创建新交办。中间回传更新进度；只有最终审批结果回传才进入纠偏节点，“拟同意”不能越过纠偏直接进入分析库或本系统办结。

## 3. 当前实现审计

| 环节 | 现有内容 | 当前判定 |
| --- | --- | --- |
| 页面框架 | 诉求管理、敏感交办、地址纠偏、交办归档、分析报告等菜单和页面存在 | 可展示原型 |
| 诉求总账 | `ComplaintList.tsx` 生成 86 条本地 Mock，搜索/筛选只针对该数组，详情链接固定到 `/complaints/1` | 未接真实总账；无手动分配动作 |
| 诉求详情 | `ComplaintDetail.tsx` 固定一条示例和处理时间线，其他 ID 回退到示例 | 未接持久化详情、真实处理轨迹 |
| 服务端诉求 | `server/src/index.js` 启动时随机生成 200 条内存数据；提供列表/详情和宜接就办模拟接收接口 | 重启丢失；前端总账未使用这些接口 |
| 敏感识别与交办 | 文本规则和交办接口雏形存在；交办列表从敏感诉求随机生成，另有无关联诉求 ID 的手动新建 | 未形成唯一业务记录；会重复交办 |
| 推送与同步 | push、sync、callback 接口返回模拟成功并只写内存日志；页面按钮仅弹成功提示 | 未连同级填报平台，未保存 ACK/事件/失败重试 |
| 反馈后处理 | 地址纠偏、归档、报告页面为 Mock；回调未更新诉求、交办和分析记录 | 目标流程下半段缺失 |
| 宜接就办 | 接收和状态同步为占位接口 | 正式对接待后续联调 |

证据入口：`packages/web-admin/src/views/ComplaintList.tsx`、`ComplaintDetail.tsx`、`DispatchOrders.tsx`、`AddressCorrection.tsx`、`DispatchArchive.tsx`、`server/src/index.js`。现有分析大屏、企业、网格、停供、施工等页面也含静态/随机数据；不能以菜单存在判为业务可用。当前工作树已有未提交修改，实施时须先保留并逐文件核对。

## 4. 实现方案

### 4.1 数据总账和状态模型

沿用现有 React 页面结构，建立持久化服务端总账。至少保存：诉求 ID、来源系统及来源 ID、原始快照、接收时间、业务分类、责任企业、敏感命中与人工标记、当前督办状态、宜接就办状态快照、纠偏前后值、分析入库标记、报告关联和审计轨迹。`(source_system, source_id)` 唯一；每次外部重传保留接收日志，必要字段变更追加版本记录。

交办是诉求的独立子实体，保存交办编号、诉求 ID、企业主体、触发类型、原因、模板及审批版本、交办要求、截止时间、来源请求号、填报任务 ID、推送和回传状态。一个诉求同一轮督办只能有一条有效交办；追加催办、补正、转交记录，不靠删除重建。

建议分开保存三条状态轴：来源事件状态、督办交办状态、填报审批状态。页面组合展示，服务端按允许的状态转换推进。“本系统办结”单独记录确认人、时间和依据；不得据此修改来源事件状态。

### 4.2 诉求总账和敏感交办页面

总账默认显示全部诉求并支持分页、来源/状态/企业/敏感规则筛选；行内提供查看、匹配/调整交办单位、手动决定敏感交办或无需交办归库。选定敏感交办且单位明确时，一次性生成交办记录并跳转“敏感交办”查看；已经有有效交办时按钮改为“查看交办”，避免重复创建。自动敏感词命中但单位缺失时按第 2 节建议保留“待匹配”，不展示为已交办。

敏感词规则保存词条、范围、版本、命中证据和审核结果。人工可以补充标记，也可以判定误报并归库。敏感交办列表按真实交办记录查询，操作限定为推送、失败重试、催办、查看企业/审批状态、回传核对和归档；删除历史交办按钮改为受控撤销并保留审计，绝不提供第二次“新建交办”。

### 4.3 跨系统任务与回传

`gqxq` 以已登记应用凭证向 `POST /api/integrations/{app}/tasks` 发起签名请求，`sourceAppCode=gqxq`、`sourceBusinessId=诉求/交办稳定 ID`、`requestId=交办唯一请求号`。任务引用已发布表单模板、版本、企业主体和审批定义。收到响应后持久化填报任务 ID 与 ACK；超时先查询/使用同请求号重试，不能另建交办。

`public-utility` 回传事件携带事件 ID、交办/来源业务 ID、企业事项、企业处置结果、模板和提交版本、附件元数据、审批结论与轨迹。`gqxq` 先验签、按事件 ID 去重并写入原始事件和处理结果，然后推进本地状态；同一事件重复投递只返回同一 ACK。签收、提交、退回和最终审批需分别可追踪；“拟同意”不得触发最终完成。

### 4.4 回传后的纠偏、分析与报告

最终结果回传后生成纠偏检查项：企业名称/归属、地址、分类、坐标、诉求摘要及企业处置结果逐项确认。改动保存旧值、新值、依据和操作者；无法确认的留在待纠偏，不假装完成。纠偏确认后才写入分析库，并建立“待查报告”记录；待查报告从分析库读取同一份已确认数据，可下钻回原诉求、交办、表单、审批和纠偏轨迹。报告如何形成、是否需要审核/发布，以及未交办归库诉求是否纳入同一分析口径，均留作业务规则确认，不能用页面占位或自动成功提示代替。

### 4.5 宜接就办预留

定义读取事件详情/状态的适配器契约、来源 ID 映射和最近同步时间字段；本期使用禁用开关和契约测试。接入前不把模拟 `200`、随机状态或填报结论显示为宜接就办真实状态。

## 5. 落地顺序与验收门槛

| 批次 | 可交付结果 | 必须通过的验收 |
| --- | --- | --- |
| G1 总账真实化 | 持久化诉求、来源去重、真实列表/详情和审计时间线 | 重启后数据仍在；全部接收诉求可查；任意行打开对应 ID |
| G2 分配与分流 | 总账人工分配、自动/人工敏感识别、无需交办归库、唯一交办 | 误报归库无任务；重复操作不生成第二张交办 |
| G3 填报集成 | 已发布模板绑定、签名推送、ACK/重试和状态查询 | 同一请求多次推送在两系统都只对应一个任务 |
| G4 回传闭环 | 事件验签、幂等接收、签收/提交/审批结果和版本轨迹 | 企业退回重提与最终同意后，诉求和交办页面显示一致结果；重复回传无重复业务结果 |
| G5 回传后流程 | 最终回传生成纠偏待办；确认后分析入库并进入待查报告；保留独立的“本系统办结”状态 | 未纠偏不得进入分析库；可从待查报告追溯诉求、交办、表单、审批与纠偏历史 |
| G6 来源对接 | 宜接就办只读状态适配器和同步监控 | 获得接口后按来源 ID 对账；失败不改变填报结果或本系统办结 |

每批验收都要在浏览器以真实页面操作，加接口、数据库和重启后的状态核对；单个接口返回 `200` 不算通过。G1/G2 可在 `public-utility` 业务页面补齐期间独立推进，G3/G4 以双方契约联调为共同门槛。

## 6. 路线选择与需确认规则

推荐在独立 `gqxq` 中保留现有 React 页面，逐步替换 Express 内存 Mock 为持久化业务服务，并通过 API 对接同级 `public-utility`。另一条路径是把 `gqxq` 功能并入 `zhuxin-platform` 后端，能复用其既有基础设施，但会增加部署和边界耦合，与“各自系统先完善”的决定不一致。

不阻塞总账建设的待确认规则：自动敏感词命中但尚无交办单位时是否按第 2 节建议留在总账“待匹配”；敏感词命中是否自动推送或需人工复核；多企业责任的拆分口径；“本系统办结”的触发条件；未交办归库诉求的分析口径；“待查报告”的形成、审批和发布人。未确认前不得把建议写死成不可变业务规则。
